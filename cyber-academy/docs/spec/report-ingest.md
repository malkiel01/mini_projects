# קליטת דיווחי מורים ממקור מורשה — `POST api/report-ingest.php`

> **מעמד:** מימוש בענף הפיתוח `claude/aca-report-ingest`. לא ממוזג ולא נפרס. מקור הדיווחים עצמו (הכלי שבו המורים כותבים) טרם חובר.

## מה זה

נקודת כניסה מאובטחת שבה מערכת מורשית מעבירה דיווחי מורים לתוך התקדמות הלומד. **זו זהות של המקור, לא של הלומד**: הלומד לא מזין מזהים ולא נדרש לדבר עם השרת. דיווח שמגיע כאן נכתב דרך אותו נתיב כתיבה של הדיווח של המנהל (`_ap_write_action`, action `report`), עם אותה נעילה, אותו יומן ואותו מאמת.

## אימות המקור

- כותרת `Authorization: Bearer <token>` בלבד. בלי אסימון בכתובת ובלי עוגיות.
- האסימון נקרא מ-`ingest.token_file` בלבד, נתיב מוחלט **מחוץ לעץ האתר**, קובץ **לא קריא לכולם**, ואורך מינימלי 20 תווים. אסימון בתוך הקונפיג נדחה.
- השוואה בזמן קבוע (`hash_equals`).
- בקשה עם `Origin` או `Sec-Fetch-Site` נדחית (403). הקליטה היא לא מדפדפן, ולכן אין CSRF.
- כשל בהגדרה → 503 גנרי `ingest_unavailable`. הסיבה המלאה נרשמת בלוג השרת בלבד, בלי נתיב ובלי ערך.

## גוף הבקשה

```json
{
  "learnerId": "lrn-1",
  "reports": [ { "reportVersion": "1.0.0", "taskId": "ACA-...", "teacherId": "01", "date": "2026-11-20", "...": "..." } ]
}
```

- `learnerId` חייב להתאים ל-`ACADEMY_V2_ID`.
- `reports`: מערך של 1–50 דיווחים בפורמט `teacher-report-format.md`.
- כל דיווח נבדק ב-`validate-report.php`. דיווח לא תקין מסומן `invalid` עם פירוט שגיאות (בלי תוכן), ולא נכתב.

## תשובה

```json
{ "ok": true, "learnerId": "lrn-1", "results": [
  { "index": 0, "status": "stored",    "reportId": "ACA-...-T01" },
  { "index": 1, "status": "duplicate", "reportId": "ACA-...-T01" },
  { "index": 2, "status": "invalid",   "errors": ["..."] },
  { "index": 3, "status": "rejected",  "reportId": "...", "code": "progress_invalid" }
] }
```

- `stored` — נכתב לתוך ההתקדמות.
- `duplicate` — כבר נקלט. **לא נכתב שוב**, ורק שורה ביומן (`report-duplicate`).
- `invalid` — לא עבר את המאמת הנוכחי של הדיווח.
- `rejected` — עבר את מאמת הדיווח אבל נדחה בבדיקת מצב ההתקדמות.
- תגובה לא מכילה אסימון, נתיב, או תוכן ממצאים.

## כפילויות

מזהה הדיווח הוא `taskId-T<teacherId>`. המאמת של ההתקדמות דוחה מזהה כפול, ולכן הכפילות מטופלת לפני הכתיבה: הדיווח נבדק שוב עם מזהה זמני, כדי שכל שאר הבדיקות ירוצו גם בקליטה חוזרת, ורק אז מוחזר `duplicate`. **שליחה חוזרת של אותה קבוצה בטוחה.**

הכפילות מטופלת גם בנתיב הכתיבה של המנהל (`action: report`): גם שם דיווח שכבר קיים לא נכתב שוב, והתגובה היא `duplicate: true`.

## כשל באמצע קבוצה

כל דיווח נכתב בנפרד. אם כתיבה נכשלת באמצע הקבוצה, הדיווחים שכבר נכתבו נשארים, והתשובה היא 503. **שליחה חוזרת של אותה קבוצה בטוחה** בזכות מנגנון הכפילויות.

## מה לא נכלל במימוש הזה

- חיבור למקור הדיווחים עצמו (ChatGPT או כלי אחר). זה דורש החלטה נפרדת על המקור ועל האסימון.
- ייבוא חד-פעמי של דיווחי Linux קיימים. אין במאגר רשומות כאלה, רק דוגמאות סינתטיות.
- הפרדה בתצוגה בין "תורגל" לבין "דווח". כיום יש רק קטגוריית "דווח וממתין לאימות". הפרדה נוספת דורשת שינוי במודל הנתונים, וזו החלטה של מנהל 00.
- שיוך אוטומטי לזהות השער. הקישור `sub → learnerId` נשמר ב-`learners.json` על ידי פעולת ה-`register` של המנהל, פעם אחת.

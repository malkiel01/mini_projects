# אפיון: בונה שיטות בהגדרות המערכת + שכבת תחזית על הגרף — טיוטה לאישור

## 1. מטרה

היום שיטה = מודול PHP ב-`lib/methods/<id>.php` (spec-stage-a 6.1) ו"שיטות שמשתמש מגדיר" נדחו לעתיד (פרק 16).
המטרה: **ליצור שיטה חדשה מתוך מסך ההגדרות, בלי קוד**, ולהציג את תחזיותיה כשכבה על גרף.

## 2. שני סוגי שיטות

| סוג | מי מגדיר | דוגמה |
| --- | --- | --- |
| **קוד** (קיים) | מפתח — לוגיקה שאי אפשר לתאר בכללים פשוטים | גלי אליוט (זיהוי דפוסים) |
| **מוגדר** (חדש) | מנהל, במסך "שיטות" | חציית ממוצעים, RSI + רמות, פריצת טווח |

**הכרעה נדרשת:** אליוט, בגלל מורכבות הזיהוי, אינו ניתן לביטוי כהגדרה בלבד. הצעה: **שני הסוגים חיים יחד** ובונה
השיטות מגדיר גם את מה שמודול-קוד חושף (שם, פרמטרים, תצוגה). בשלב מאוחר — "אבני בניין" (pivots, פיבונאצ'י, ערוצים)
שהגדרה יכולה להשתמש בהן, כך שגם שיטות כמו אליוט יורכבו מהגדרה.

## 3. מודל ההגדרה (JSON, נשמר ב-`methods.definition`)

```
{
  "id": "my-method", "name": "...", "source": "...", "version": 1,
  "markets": [...], "timeframes": [...],
  "params": { "key": {"label","default","min","max","int"} },
  "indicators": [ {"id":"ma_fast","type":"sma","source":"close","length":"$fast"} ],
  "rules": {
     "long":  { "all": [ {"left":"ma_fast","op":"crosses_above","right":"ma_slow"} ] },
     "short": { "all": [ ... ] }
  },
  "levels": { "stop":"entry - 2*atr14", "target":"entry + 3*atr14" },
  "horizon_bars": 50,
  "forecast": { "type": "levels|projection|none", ... },
  "display": { "overlays": [ ... ] }
}
```

- ביטויים בשפה **סגורה ובטוחה** (מנתח משלנו — מספרים, אינדיקטורים, `+ - * /`, השוואות, `crosses_*`, `and/or`).
  **אין `eval`, אין קוד חופשי, אין רשת.**
- אינדיקטורים מהספרייה הקיימת (`lib/indicators.php`: SMA, EMA, RSI, ATR, נפח). הרחבה ע"י הוספת סוג — בקוד.
- **הגדרה → TsMethod:** מתאם אחד (`TsDefinedMethod`) שמממש את `meta/init/step/conditions` מתוך ה-JSON, כך
  שכל מנוע הבדיקה לאחור, הניתוח והשקלול עובדים **בלי שינוי**. אותן הבטחות: טהור, בלי הצצה לעתיד, מצטבר = מלא.

## 4. מסך הניהול (עוד ← שיטות, מנהל)

- רשימת שיטות (קוד + מוגדרות), פעילה/כבויה (כמו 6.7). "➕ שיטה חדשה".
- עורך: פרטים · פרמטרים · אינדיקטורים · כללי לונג/שורט (בונה חזותי של תנאים) · רמות · אופק · תחזית ותצוגה.
- **אימות לפני שמירה:** תחביר, הפניות, טווחי פרמטרים, והרצה על סט נרות לדוגמה ("🧪 נסה") — מציג אותות ותנאים.
- **גרסאות:** כל שמירה משנה את ההגדרה ← `version+1` ← בדיקות לאחור מחושבות מחדש (6.7). היסטוריית גרסאות נשמרת.
- שיטה חדשה — **כבויה** עד הפעלה. שיטה מוגדרת חדשה מסומנת "מוגדרת ידנית" עד שעברה בדיקה לאחור עם N≥30.
- הרשאות: מנהל בלבד (`ts_require_admin()`), כל שינוי ב-`admin_log`. **הצעה:** משתמש רגיל לא מגדיר שיטות (נשאר
  בפרק 16) — האם לפתוח בהמשך? **להכרעה.**

## 5. שכבת תחזית על הגרף

המשתמש עומד על גרף ← בוחר שיטה מתפריט "🔮 תחזית לפי שיטה" ← השיטה רצה על **הנרות המוצגים (טווח התקופה בגרף)**
ומחזירה `overlay`; הגרף מצייר אותו, כולל **הקרנה של המשך המסלול**.

### 5.1 חוזה ה-overlay (מוחזר מ-`analyze`, נוסף ל-6.1)

```
overlay: {
  as_of: t, range: {from, to},
  items: [
    {"kind":"label",   "t","price","text"},                       // תווית על נר (גל 3, סימן אות)
    {"kind":"polyline","points":[{t,price}...],"style":"solid|dashed"},   // קו ספירה / הקרנה
    {"kind":"zone",    "t1","t2","p1","p2","text"},               // אזור יעד/תמיכה
    {"kind":"hline",   "price","text","role":"stop|target|invalidation"},
    {"kind":"marker",  "t","side","text"}
  ],
  "projection": { "bars": N, "scenarios":[ {"id","score","points":[...],"label"} ] }
}
```

- זמנים עתידיים מחושבים מצעד המסגרת (`t + k·tf`); הגרף מרחיב את ציר הזמן ימינה כדי להציג אותם (Lightweight Charts
  תומך ב-whitespace data).
- **טווח:** מחושב מהנרות הנראים בגרף; שינוי טווח/מסגרת → לחיצה על "רענן" (✅13: אין רענון אוטומטי).
- `scenarios` — כמה תרחישים עם ציון; העליון מודגש, האחרים עמומים.
- הכול **float לתצוגה בלבד** (עיקרון 6), כמו האינדיקטורים.

### 5.2 מגבלות וניסוח

- התחזית **תרחיש לפי כללי השיטה**, לא ניבוי. כותרת: "תרחיש לפי שיטת X — לא ייעוץ", עם ההסתייגות הקבועה (6.6).
  ללא "קנה/מכור", ללא אחוז בלי מקורו. שיטה ללא בדיקה לאחור מסומנת "לא נבדקה לאחור".
- **התנגשות עם 6.4** ("לא מציגים מעבר לאופק שנבדק") — הצעה: להבדיל בין **"ניתוח"** (כפוף ל-6.4) לבין **"תחזית
  חזותית"** (מותרת עד `forecast.bars` של השיטה, מסומנת במפורש). **להכרעה.**
- הקרנה לא נכנסת לשקלול (6.5) ולא להתראות, אלא אם הוגדרה שיטה עם אותות ובדיקה לאחור.

## 6. נתונים

- `methods`: עמודות חדשות `kind` (`code|defined`), `definition(json)`, `definition_version`; טבלת `method_versions`
  (method_id, version, definition, saved_by, saved_at).
- שרת: `admin_method_save|validate|dry_run|list|versions`, `method_overlay` (ניתוח + overlay לנכס/מסגרת/טווח).
- מנגנון ה-`registry.php`: שיטות מוגדרות נטענות מהמסד ליד אלה שבקוד; מזהה שמתנגש עם שיטת קוד — נדחה.

## 7. בדיקות (נכתבות לפני הקוד)

- הגדרה ← `TsDefinedMethod` נותנת **אותם אותות** כמו `sample-ma-cross` כשמגדירים אותה כהגדרה (שוויון להתנהגות הקיימת).
- אי-הצצה, דטרמיניזם, מצטבר = מלא — על שיטה מוגדרת.
- מנתח ביטויים: קלט זדוני (קריאות פונקציה, גישה לקבצים, לולאות, מחרוזות ארוכות) — נדחה; תקרת עומק ואורך.
- הרשאות: משתמש לא-מנהל מקבל 403 בכל `admin_method_*`; שמירה נרשמת ב-`admin_log`.
- overlay: זמני הקרנה מיושרים למסגרת; נקודות לפי חוזה; הגרף לא פונה לשרת בלי פעולה (no-polling).

## 8. שלבי פיתוח מוצעים (PR-ים)

1. מנתח ביטויים + `TsDefinedMethod` + בדיקות שוויון ל-`sample-ma-cross` (בלי UI).
2. חוזה overlay + שכבת תחזית בגרף (עם שיטת הדוגמה).
3. מסך בונה השיטות (מנהל) + גרסאות + "🧪 נסה".
4. שיטת גלי אליוט כמודול קוד (spec-elliott-wave.md), אחרי אישור הסיכום מול הספר.
5. (עתידי) אבני בניין, ושיטות שמשתמש רגיל מגדיר.

## 9. החלטות פתוחות לאישור

1. תחזית חזותית לעומת 6.4/6.6 (סעיף 5.2).
2. אליוט כקוד ובהמשך אבני בניין (סעיף 2).
3. מי מגדיר שיטות — מנהל בלבד בשלב זה (סעיף 4).
4. אליוט לבדיקה לאחור, בנוסף לשכבה החזותית (spec-elliott-wave פרק 6).

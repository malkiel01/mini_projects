# 02 — הזמנות דרך המעטפת, ומצב מנותק

**תלויה ב-01.** משלימה את ההתחברות לפי `platform/docs/auth.md`: הזמנת עובד שאין לו
עדיין חשבון במעטפת, והתנהגות המערכת כשהיא **מנותקת** (המנהל ניתק אותה במעטפת, או
שהיא יצאה לדומיין משלה).

קריאת חובה: `platform/docs/sso.md` (כולו), `platform/docs/embed.md` סעיפים 1–2
(החתימה על בקשות שרת-לשרת), `platform/docs/auth.md` סעיפים 2, 4, 6.

## 1. מה בונים

1. **הזמנה שפותחת חשבון:** מנהל משרד מזמין מייל ← המערכת מבקשת מהמעטפת לפתוח לו
   חשבון עם הרשאה ל-`appraisers` בלבד (`provision.php`), ושולחת מייל הזמנה.
2. **מפתח חתימה** של המערכת (Ed25519) ופעולת `platform_key` ציבורית.
3. **מצב מנותק:** "כניסה עם הכלים הדיגיטליים" (`sso.php`, זהות חתומה), ובנוסף סיסמה
   משלה — רק אם המנהל פתח אותה ב-`config`.
4. יציאה, שכחתי סיסמה, והגבלת ניסיונות — רק במצב מנותק.
5. אישור חוזר לפעולות רגישות (ש-40).

## 2. מה לא

- כניסה עם Google של האפליקציה — לא נבנית (אין דרישה; `login.google` מתעלמים ממנו).
- ביטול הרשאה במעטפת כשחבר מוסר ממשרד — לא נעשה אוטומטית (סעיף 6, מקרה 5).

## 3. מודל הנתונים

```
platform_keys                         מפתח החתימה של המערכת מול המעטפת
  id, kid, alg ('Ed25519')
  public_key   TEXT                   base64
  private_key  BLOB                   מוצפן ב-secret.key
  status       active | retired
  created_at

invitations  (+)
  invitee_sub        TEXT NULL        ה-sub שהמעטפת החזירה ב-provision
  provision_status   TEXT NULL        invited | granted | blocked | failed | skipped
  email_sent_at      TEXT NULL
  email_status       TEXT NULL        sent | failed

users  (+)
  password_hash      TEXT NULL        רק למצב מנותק; password_hash() של PHP
  must_change_pw     INT

login_attempts
  key (מייל או IP), count, locked_until

sso_states                            מצב חד-פעמי לזרימת sso.php
  state_hash, created_at, expires_at, used_at

sso_jti                               מניעת שימוש חוזר בזהות חתומה
  jti, exp

password_resets
  user_id, token_hash, expires_at, used_at

mail_log                              כל מייל שהמערכת שולחת
  id, at, kind (invite | reset | otp …), to_hash, status (sent | failed),
  error TEXT NULL, idempotency_key UNIQUE, office_id NULL
```

`mail_log` שומר **hash של הכתובת**, לא את הכתובת — כדי שיומן המפתח לא יחשוף נמענים.

## 4. הזמנה דרך המעטפת

### 4.1 ההצהרה ב-`app.json`

```json
"provision": { "key_url": "https://mbe-plus.com/mini_projects/appraisers/api.php?action=platform_key" },
"sso": { "return": ["https://mbe-plus.com/mini_projects/appraisers/api.php?action=sso-callback"] }
```

ול-`public` מתווספים: `api.php?action=…|platform_key|sso-start|sso-callback|login|forgot|reset|login-config`.

`platform_key` מחזיר `{"client":"appraisers","keys":[{"kid","alg":"Ed25519","key"}]}`.
המפתח נוצר בהרצה הראשונה; הפרטי נשמר מוצפן במסד, **לא בגיט**.

### 4.2 הזרימה

1. מנהל משרד מזין מייל, שם, תפקיד ← נוצרת הזמנה (כמו ב-01).
2. המערכת שולחת `POST platform/provision.php`, חתום:
   `{"email","name","grant":true,"next":"/mini_projects/appraisers/"}`.
3. לפי התשובה:

| תשובה | מה המערכת עושה | מה המנהל רואה |
| --- | --- | --- |
| `invited` + `sub` | שומרת `invitee_sub`. המעטפת שולחת למוזמן מייל לבחירת סיסמה | "נשלחה הזמנה. המוזמן יקבל מייל לבחירת סיסמה." |
| `granted` + `sub` | שומרת `invitee_sub`. למוזמן כבר יש חשבון במעטפת | "למוזמן יש כבר חשבון; נשלח לו קישור להצטרפות." |
| `blocked` | ההזמנה נשארת, `provision_status = blocked` | "אי אפשר להזמין את הכתובת הזו. פנו למנהל המערכת." |
| שגיאה / אין תשובה | `failed`; משימת רקע מנסה שוב 3 פעמים | "ההזמנה נשמרה, אבל פתיחת החשבון נכשלה. ננסה שוב; אפשר גם להעתיק את הקישור." |

4. **בכל מקרה שאינו `blocked`** המערכת שולחת מייל משלה: "הוזמנת למשרד X", עם
   הקישור `…/appraisers/#/invite/<אסימון>`.
5. כשהמוזמן נכנס (אחרי בחירת סיסמה במעטפת, או ישר אם היה לו חשבון): אם ה-`sub`
   שלו שווה ל-`invitee_sub` של הזמנה ממתינה — היא מוצגת לו ב"יש לי הזמנה" **גם
   בלי התאמת מייל מאומת**. ההצטרפות עצמה נשארת לחיצה מפורשת.

"📋 העתקת קישור" מ-01 נשאר, כגיבוי.

### 4.3 כללים

- בקשת `provision` נשלחת **רק** בפעולת הזמנה של מנהל משרד פעיל, ורק למייל אחד בכל פעם.
- הגבלה: עד 20 הזמנות למשרד ביום 🟡. מעבר לזה — "הגעתם למגבלת ההזמנות היומית".
- כשהמעטפת לא עונה — **נכשלים סגור**: לא מניחים שהחשבון נפתח.
- מייל שנכשל אינו מוצג כנשלח. למנהל: "המייל לא נשלח — העתיקו את הקישור".

## 5. מצב מנותק

המערכת קוראת `platform/sso.php?action=config&client=appraisers` (מטמון של 60 שניות):
`{"connected": false, "login": {"platform": true, "password": bool, "google": bool}}`.

### 5.1 מסך הכניסה (קיים רק במצב מנותק)

- **"כניסה עם הכלים הדיגיטליים"** — תמיד.
- **מייל וסיסמה** — רק כש-`login.password` הוא `true`.
- כש-`config` לא עונה: "הכניסה לא זמינה כרגע. נסו שוב בעוד דקה." — בלי טופס.

### 5.2 כניסה עם הכלים הדיגיטליים

`sso-start`: יוצר `state` אקראי (32 תווים), שומר את ה-hash שלו, ומפנה ל-
`platform/sso.php?client=appraisers&state=…&return=<כתובת החזרה>`.

`sso-callback` בודק **הכול**, לפי `sso.md` סעיף 2:

1. `state` קיים, לא נוצל, לא פג (10 דקות) — ומסומן כנוצל מיד.
2. `error` בכתובת ← חזרה למסך הכניסה עם "הכניסה בוטלה".
3. החתימה תקינה במפתח הציבורי של המעטפת (`sso.php?action=key`, נשמר במטמון 24 שעות;
   חתימה שנכשלה ← מרעננים את המפתח פעם אחת ובודקים שוב).
4. `aud` = `appraisers`; `iss` = כתובת המעטפת; `return` = כתובת החזרה שלנו; `exp` לא עבר.
5. `jti` לא נראה קודם (נשמר עד `exp`).

עבר ← אותו טיפול כמו בזהות מהשער (01 סעיף 5.2, שלבים 3–9): קישור לפי `sub`, איחוד
לפי מייל מאומת, או חשבון חדש. נכשל ← "הזהות לא תקפה", ושורה ביומן עם הסיבה
הטכנית (בלי האסימון).

### 5.3 סיסמה משלה

- קביעת סיסמה: בתפריט המשתמש, **רק כשמחוברים** (במצב מחוברת או אחרי כניסה מאוחדת).
  לפחות 10 תווים. מי שלא קבע — אין לו כניסה בסיסמה.
- כניסה: מייל + סיסמה. 5 כשלים ← נעילה של 15 דקות, לפי מייל ולפי IP.
  ההודעה זהה למייל לא קיים ולסיסמה שגויה.
- שכחתי סיסמה: מייל עם קישור (שעה, שימוש אחד). התשובה תמיד "אם הכתובת רשומה —
  נשלח מייל".
- שינוי סיסמה מנתק את שאר ה-sessions של המשתמש.
- **במצב מחוברת הכניסה בסיסמה חסומה לגמרי** (403), גם אם נקבעה. הסיסמה נשמרת,
  וחוזרת לעבוד כשהמערכת מנותקת.

### 5.4 יציאה

במצב מנותק יש "יציאה" בתפריט: מוחקת את ה-session ואת העוגייה. במצב מחוברת — אין
(יוצאים מהמעטפת).

### 5.5 חזרה למצב מחוברת

כשהשער חוזר לפעול, הזהות מגיעה שוב ב-`PLATFORM_USER`, והכללים של 01 חלים. חשבון
שנוצר בסיסמה בלבד ואין לו `platform_sub` — מתקשר לפי מייל מאומת; אין מייל תואם
במעטפת ← אין לו איך להגיע (השער חוסם), וזה ההתנהגות ש-`auth.md` סעיף 4 קובע.

## 6. אישור חוזר לפעולות רגישות

רשימת הפעולות היא נתון (`sensitive_actions`), ופרוסות מאוחרות מוסיפות אליה:
השעיית משרד, הענקת מנהל מערכת, יצירת אסימון DevLoop, ובהמשך — מפתח בינה, גישת
תמיכה, אישור דוח.

- **במצב מחוברת:** חלון אישור עם תיאור מדויק של הפעולה והקלדת מילת אישור ("אישור").
- **במצב מנותק:** קוד בן 6 ספרות למייל (10 דקות, 5 ניסיונות), תקף ל-10 דקות של
  פעולות רגישות באותו session.
- האישור נרשם ביומן הפעולות יחד עם הפעולה.

| תפריט משתמש (עדכון) | "סיסמה לכניסה נפרדת", ובמנותק — "יציאה" | תמיד |

## 8. הרשאות

| פעולה | מי |
| --- | --- |
| הזמנה עם `provision`, שליחה שוב | מנהל משרד פעיל, במשרד שלו |
| `platform_key`, `sso-start`, `sso-callback`, `login`, `forgot`, `reset`, `login-config` | בלי משתמש (ציבוריות) |
| קביעת סיסמה | המשתמש עצמו, כשהוא מחובר |
| רשימת `mail_log` | מפתח (hash בלבד, מצב ושגיאה) |

## 9. מקרי קצה

1. **המוזמן כבר חבר במשרד.** לא נשלחת בקשת `provision`; "כבר חבר/ה במשרד".
2. **אותו מייל מוזמן פעמיים ברצף.** מזהה פעולה; בקשת `provision` אחת, מייל אחד.
3. **`provision` הצליח, המייל שלנו נכשל.** ההזמנה תקפה; המנהל רואה "המייל לא נשלח".
4. **`provision` נכשל, ואחר כך הצליח בניסיון חוזר.** `invitee_sub` מתעדכן; לא נשלח
   מייל שני אם הראשון כבר יצא.
5. **חבר הוסר מהמשרד האחרון שלו.** ההרשאה במעטפת **נשארת** — הוא יכול להקים משרד
   משלו. מי שרוצה לחסום אותו לגמרי: מנהל המערכת משעה את החשבון.
6. **המפתח הציבורי של המעטפת התחלף.** חתימה נכשלת ← רענון אחד ← בדיקה חוזרת.
7. **אותה זהות חתומה נשלחת פעמיים** (לחיצה על "אחורה"). ה-`jti` כבר נוצל ← נדחה,
   והמשתמש מופנה להתחיל מחדש.
8. **שעון השרת סוטה.** סובלנות של 60 שניות על `exp`; מעבר לזה נדחה, ונרשמת אזהרה
   בבדיקות התקינות.
9. **מעבר ממחוברת למנותקת באמצע עבודה.** ה-session הקיים ממשיך עד שיפוג; כניסה
   חדשה — לפי 5.1.
10. **`login.password` נסגר במעטפת.** טופס הסיסמה נעלם תוך 60 שניות; ניסיון ישיר
    ל-`login` ← 403.

## 10. קריטריוני קבלה

- **02-A1** 🤖 `platform_key` מחזיר מפתח תקין; המפתח הפרטי אינו מופיע בשום תשובת API
  ואינו בגיט (בדיקה סטטית: אין מחרוזת מפתח בקוד).
- **02-A2** 🤖 הזמנה עם תשובת `invited` (מעטפת מדומה) ← `invitee_sub` נשמר; זהות עם
  אותו `sub` ו**מייל לא מאומת** רואה את ההזמנה ויכולה להצטרף.
- **02-A3** 🤖 תשובת `blocked` ← לא נשלח מייל, והמנהל מקבל את הנוסח המתאים.
- **02-A4** 🤖 המעטפת לא עונה ← ההזמנה נשמרת, נוצרת משימת רקע לניסיון חוזר, ולא
  נרשם `invitee_sub`.
- **02-A5** 🤖 אותה הזמנה נשלחת פעמיים עם אותו מזהה פעולה ← בקשת `provision` אחת
  ושורה אחת ב-`mail_log`.
- **02-A6** 🤖 חבר שאינו מנהל אינו יכול לגרום לבקשת `provision`.
- **02-B1** 🤖 `sso-callback` דוחה: חתימה שגויה; `aud` אחר; `state` שלא נוצר כאן;
  `state` שכבר נוצל; `exp` שעבר; `return` אחר; `jti` שכבר נראה. (שבע בדיקות נפרדות.)
- **02-B2** 🤖 זהות חתומה תקינה ← נוצר session, והמשתמש הוא החשבון המקושר ל-`sub`.
- **02-B3** 🤖 במצב מחוברת `login` בסיסמה ← 403, גם עם סיסמה נכונה.
- **02-B4** 🤖 במצב מנותק עם `login.password: false` ← 403; עם `true` וסיסמה נכונה ←
  session.
- **02-B5** 🤖 5 כשלי כניסה ← הניסיון השישי נדחה גם עם הסיסמה הנכונה, למשך 15 דקות.
- **02-B6** 🤖 מייל לא קיים וסיסמה שגויה מחזירים אותה תשובה בדיוק; `forgot` מחזיר
  אותה תשובה לכתובת רשומה וללא רשומה.
- **02-B7** 🤖 קישור איפוס עובד פעם אחת בלבד, ולא אחרי שעה.
- **02-B8** 🤖 שינוי סיסמה מבטל את שאר ה-sessions של אותו משתמש.
- **02-C1** 🤖 פעולה רגישה בלי אישור חוזר ← 403 עם קוד `confirm_required`; עם אישור
  ← מתבצעת, ושתי השורות ביומן הפעולות.
- **02-C2** 🤖 ב-`mail_log` אין אף כתובת מייל בטקסט גלוי.
- **02-D1** 👁 מנהל מזמין כתובת שאין לה חשבון ← מגיעים שני מיילים (בחירת סיסמה
  מהמעטפת, והזמנה למשרד); אחרי בחירת הסיסמה המוזמן רואה את ההזמנה ומצטרף.
- **02-D2** 👁 חלון גלישה בסתר: `platform_key` מחזיר JSON (לא 401).
- **02-D3** 👁 מנתקים את האפליקציה בממשק המנהל של המעטפת ← מופיע מסך הכניסה עם
  "כניסה עם הכלים הדיגיטליים", והכניסה עובדת. מחברים מחדש ← המסך נעלם.

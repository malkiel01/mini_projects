## 1. מה נכנס ומה לא

| נכנס | לא נכנס (מתי) |
| --- | --- |
| מסמכי JSON לפי אוסף ומפתח, במרחב `user` ובמרחב `app` | העדפות משותפות `prefs` (שלב 6) |
| `rev` ו-`if_rev`, רשימה, שינויים מאז (`changes`), 5 גרסאות לכל מסמך | שאילתות על תוכן המסמך (לעולם לא, סעיף 2) |
| מכסה לכל אפליקציה, ותקרה למסמך | נתון גדול כקובץ בתיקייה מוסתרת (אחרי `files.app`, שלב 3) |
| "🗑️ מחק נתונים", מדף הענן ומהאפליקציה | סנכרון לא-מקוון ב-IndexedDB בתוך המודול. האפליקציה בונה אותו על `changes`, ובהמשך הוא ייכנס למודול |
| `account_export` כולל את `appdata` של המשתמש | |
| `drives.appdata` במודול, והלשונית "🧩 נתוני אפליקציות" | |

## 2. המבנה — אוסף, מפתח, מסמך JSON (שאלה 1)

**תשובה: "שניהם" במובן הזה:** לכל אפליקציה יש אוספים (`collection`). בכל אוסף, כל מפתח (`key`) מחזיק מסמך JSON אחד.
זה key-value שבו הערך הוא מסמך, ואין מנוע שאילתות. מי שצריך אינדקס מחזיק אותו כמסמך משלו.

| שדה | כלל |
| --- | --- |
| `space` | `user` (ברירת המחדל) או `app` |
| `collection` | `^[a-z0-9][a-z0-9_-]{0,63}$`. למשל `settings`, `charts`, `watchlist` |
| `key` | 1–200 תווים, UTF-8 ב-NFC, בלי תווי בקרה. אפשר `/` לקיבוץ (`2026/11/btc`), אבל זו לא תיקייה |
| `value` | כל JSON תקין (אובייקט, מערך, מחרוזת, מספר, `true`/`false`). `null` אסור, ובמקומו מוחקים. **עד 256KB** אחרי קידוד |

```sql
CREATE TABLE IF NOT EXISTS appdata (
    client      TEXT NOT NULL,                 -- מהחתימה או מהאסימון, לעולם לא מהגוף
    space       TEXT NOT NULL CHECK (space IN ('user','app')),
    account     TEXT NOT NULL,                 -- '' במרחב app
    collection  TEXT NOT NULL,
    key         TEXT NOT NULL,
    value       TEXT NOT NULL,                 -- JSON
    size        INTEGER NOT NULL,              -- strlen(value)
    rev         INTEGER NOT NULL,              -- 1, 2, 3… לכל מסמך
    seq         INTEGER NOT NULL,              -- מונה עולה אחד לכל הטבלה, בשביל changes
    updated_at  TEXT NOT NULL,
    updated_by  TEXT NOT NULL DEFAULT '',      -- החשבון, או 'server' במרחב app
    deleted_at  TEXT,                          -- מצבה (tombstone) ל-changes. נמחקת לצמיתות אחרי 30 יום
    PRIMARY KEY (client, space, account, collection, key)
);
CREATE INDEX IF NOT EXISTS appdata_seq ON appdata(client, space, account, seq);

CREATE TABLE IF NOT EXISTS appdata_history (   -- 5 הגרסאות הקודמות, 30 יום
    client TEXT, space TEXT, account TEXT, collection TEXT, key TEXT,
    rev INTEGER, value TEXT, size INTEGER, at TEXT,
    PRIMARY KEY (client, space, account, collection, key, rev)
);
```

## 3. בידוד (שאלה 3)

- **כן: כל `client` רואה רק את שלו.** ה-`client` נלקח מהחתימה (`X-Cloud-Client`) או מה-`aud` של האסימון, **לעולם לא
  משדה בגוף**. אין פרמטר שמאפשר לבקש `client` אחר.
- **במרחב `user`:** ה-`account` נלקח מהחיבור. הכלל "אותו חשבון" (`spec-0` 6.3) כבר מבטיח שזה המשתמש עצמו.
- **ההיקף `appdata`** נדרש לכל פעולה. בלעדיו מוחזר `403 forbidden` עם `{"scope":"appdata"}`, והמודול מתרגם אותו
  ל-`layer-off`.
- **מנהל הענן לא רואה את התוכן**, גם לא בממשק הניהול. הוא רואה רק נפח.
- **`prefs` אינו חלק משלב 4.** הוא שלב 6, ההיקף שלו נפרד, ואין שום דרך לקרוא בו נתונים של אפליקציה אחרת.

## 4. מרחב `app`

| | קריאה | כתיבה ומחיקה |
| --- | --- | --- |
| **שרת האפליקציה** (חתום, **בלי** `X-Cloud-Connection`) | ✓ | ✓ |
| **הדפדפן** (אסימון של משתמש עם `appdata`) | ✓ | ✗ → `403 forbidden` |
| **שרת האפליקציה בשם משתמש** (חתום, עם חיבור) | ✓ | ✗. כותבים במרחב `app` רק בלי חיבור, כדי שיהיה ברור שזו כתיבה של האפליקציה ולא של משתמש |

- `account = ''`, ו-`updated_by = 'server'`.
- **אפליקציה בלי אף חיבור פעיל** עדיין יכולה לכתוב, כי היא לקוח רשום ופעיל. לקוח שמנהל הענן כיבה (`disabled`) לא
  יכול לא לקרוא ולא לכתוב.

## 5. מגבלות ומכסה (שאלה 2)

| מגבלה | ערך | נקבע ב |
| --- | --- | --- |
| מסמך אחד | **256KB** | קבוע |
| `user`: לכל זוג (אפליקציה, משתמש) | **20MB** ברירת מחדל | ⚙️ ניהול ← אפליקציות ← האפליקציה |
| `user`: לכל משתמש, בכל האפליקציות יחד | **100MB** ברירת מחדל | ⚙️ ניהול ← הגדרות |
| `app`: לכל אפליקציה | **50MB** ברירת מחדל | אותו מקום |
| מסמכים באוסף | בלי הגבלה, וכל מה שנספר הוא הנפח | — |

- **הנפח שנספר:** `SUM(size)` של מסמכים חיים. מצבות וגרסאות לא נספרות.
- **`user` לא נספר במכסת הכונן** (הכרעה ש1, סעיף 9). יש לו שתי תקרות משלו: לכל אפליקציה, ולכל משתמש בכל האפליקציות
  יחד. משתמש שהמכסה שלו בכונן היא 0 שומר הגדרות כרגיל. בדף הענן הנפח מוצג בלשונית "🧩 נתוני אפליקציות", ולא בפס של
  הכונן.
- **`app` לא נספר במכסה של אף משתמש.** הוא של האפליקציה.
- **חריגה:** `413 quota_exceeded` עם `{quota, used, scope: "app" | "user" | "account"}`. `account` מציין את התקרה של המשתמש בכל האפליקציות. מסמך מעל 256KB מחזיר `413 too_large`.

## 6. גרסאות, התנגשויות ושינויים (שאלה 4)

**כן: `rev` ו-`if_rev`, כמו בקבצים.**

- `rev` מתחיל ב-1 ועולה בכל כתיבה. מחיקה ויצירה מחדש ממשיכות מאותו מונה, ולא חוזרות ל-1.
- **`if_rev: N`** פירושו "רק אם ה-`rev` הנוכחי הוא N". **`if_rev: 0`** פירושו "רק אם המסמך לא קיים", כלומר יצירה בלבד.
  כשה-`if_rev` לא תואם מוחזר `409 conflict` עם `{rev, value}` הנוכחיים, כדי שהאפליקציה תמזג בלי קריאה נוספת.
- **בלי `if_rev`** הכתיבה דורסת. זה מותר להגדרות פשוטות, אבל המדריך ממליץ תמיד לשלוח `if_rev`.
- **`changes`:** כל כתיבה או מחיקה מקבלת `seq` חדש. `appdata_changes {since}` מחזיר את מה ש-`seq > since` שלו, כולל
  מצבות. מצבה נשמרת 30 יום. `since` ישן מזה, או `since` מעבר לשמירה, מחזיר `410 gone`, וזה סימן לטעון הכול מחדש
  דרך `list`.
- **גרסאות:** בכל כתיבה, הערך הקודם נשמר ב-`appdata_history`. נשמרות 5 גרסאות, ל-30 יום, והן לא נספרות במכסה.
  `appdata_restore {…, rev}` הוא כתיבה רגילה: הוא מחזיר ערך ישן כ-`rev` חדש.

## 7. ה-API (שאלה 7)

`api.php?action=…`, `POST` עם JSON. בכל גוף אפשר `space` (ברירת מחדל `user`).

| פעולה | גוף | תשובה |
| --- | --- | --- |
| `appdata_get` | `{collection, key}` | `{value, rev, updated_at}`. לא קיים → `404 not_found` |
| `appdata_put` | `{collection, key, value, if_rev?}` | `{rev, seq}` |
| `appdata_delete` | `{collection, key, if_rev?}` | `{ok, seq}`. לא קיים → `404 not_found` |
| `appdata_list` | `{collection?, prefix?, cursor?, limit?: 1–500 (100)}` | `{items: [{collection, key, rev, size, updated_at}], cursor}`. **בלי ערכים.** בלי `collection` מוחזרים כל האוספים |
| `appdata_get_many` | `{collection, keys: [עד 100]}` | `{items: [{key, value, rev, updated_at}]}`. מפתח שלא קיים לא מופיע |
| `appdata_changes` | `{since: 0, limit?: 1–500 (100)}` | `{changes: [{collection, key, rev, seq, deleted}], cursor, more}`. `cursor` הוא ה-`seq` האחרון |
| `appdata_history` | `{collection, key}` | `{items: [{rev, size, at}]}` |
| `appdata_restore` | `{collection, key, rev, if_rev?}` | `{rev, seq}` |
| `appdata_usage` | — | `{used, quota}` של המרחב |
| `appdata_clear` | `{confirm: "clear"}` | `{ok, deleted}`. **רק `space: user`.** מוחק את כל הנתונים של האפליקציה הזו אצל המשתמש הזה, כולל גרסאות. אחרי זה `changes` מחזיר `410 gone`, והאפליקציה טוענת מחדש |

**`app.json`:** כל `appdata_*` נוסף ל-`public`, כמו `list`/`stat`/`read`. הזהות היא תמיד חתימה או אסימון, ובלעדיהם
מוחזר `401`.

**במודול (JS):**

```js
const a = drives.appdata;                       // ומרחב האפליקציה: drives.appdata.space('app')
await a.get('settings', 'chart');               // → { value, rev } | null
await a.put('settings', 'chart', value, { ifRev });   // → { rev }. התנגשות → DriveError code 'conflict', עם rev ו-value
await a.delete('settings', 'chart', { ifRev });
await a.list({ collection: 'watchlist', prefix: '2026/' });
await a.changes(since);                         // → { changes, cursor, more }
await a.clear();                                // מוחק הכול, אחרי אישור של המשתמש באפליקציה
```

## 8. מחיקה וייצוא (שאלות 5–6)

**"🗑️ מחק נתונים" — משני הצדדים:**

| מאיפה | מה | אישור |
| --- | --- | --- |
| **דף הענן**, הלשונית "🧩 נתוני אפליקציות" | שורה לכל אפליקציה עם נפח ו"עודכן…", ו-🗑️ | "למחוק את כל הנתונים של <אפליקציה> בענן? אי אפשר לשחזר." |
| **האפליקציה** (`appdata_clear`) | למשל "אפס את ההגדרות" | האפליקציה מציגה את אותה שאלה לפני הקריאה |

- **כיבוי המתג 🗂️ לא מוחק** (`spec-0` 7.3, כלל 4). המחיקה תמיד מפורשת.
- **מרחב `app`** נמחק רק בידי מנהל הענן, בניהול, או בידי השרת של האפליקציה עצמה (`appdata_delete`).
- **מחיקת חשבון בענן** (`account_delete`) מוחקת גם את כל ה-`appdata` של המשתמש, בכל האפליקציות.

**ייצוא:** כן. `account_export` כולל את מרחב `user` בלבד, מקובץ לפי אפליקציה:
`{"appdata": {"<client>": {"<collection>": {"<key>": <value>}}}}`. בלי גרסאות ובלי מרחב `app`.

## 10. בדיקות (`mbe-cloud/tests/run.php`)

| # | הבדיקה |
| --- | --- |
| ב1 | `put` ← `get` מחזיר את אותו ערך ו-`rev: 1`. `put` נוסף מחזיר `rev: 2` |
| ב2 | `if_rev` שגוי מחזיר `409 conflict` עם ה-`rev` וה-`value` הנוכחיים. `if_rev: 0` על מסמך קיים מחזיר 409 |
| ב3 | **בידוד:** אפליקציה B, עם אותו משתמש, לא רואה את המסמכים של A: `get` מחזיר 404, ו-`list` ריק. משתמש אחר באותה אפליקציה לא רואה אותם |
| ב4 | **`client` מהגוף מתעלם:** שליחת `client: "A"` בגוף מאסימון של B לא משנה דבר |
| ב5 | בלי היקף `appdata` מוחזר `403` עם `scope: "appdata"` |
| ב6 | **`app`:** כתיבה מהדפדפן מחזירה 403. כתיבה משרת חתום בלי חיבור עובדת. קריאה מהדפדפן עובדת |
| ב7 | מסמך של 256KB + 1 מחזיר `413 too_large`. חריגה מ-20MB מחזירה `413 quota_exceeded` עם `scope: "user"`, וחריגה מ-100MB בכל האפליקציות יחד מחזירה `scope: "account"`. **משתמש שהמכסה שלו בכונן היא 0 שומר מסמך בהצלחה**, ו-`usedBytes` של הכונן לא משתנה |
| ב8 | `changes`: אחרי `put`, `put` ו-`delete`, החזרה מ-`since: 0` כוללת את כולם לפי `seq`, ואת המחיקה כ-`deleted: true`. `since` מעבר לשמירה מחזיר `410` |
| ב9 | `history` מחזיר עד 5 גרסאות. `restore` מחזיר ערך ישן כ-`rev` חדש |
| ב10 | `clear`: כל המסמכים של הזוג נמחקים, אחרים לא נפגעים, ו-`changes` מחזיר `410` |
| ב11 | `account_export` כולל את מרחב `user` לפי אפליקציה, ולא את `app`. `account_delete` מוחק הכול |
| ב12 | `value: null` ו-JSON לא תקין מחזירים `400 bad_request` |

**בעלים:** הצ'אט "ענן MBE - אפיון". את הקוד כותב הצ'אט "ענן MBE - קוד". **מקור:** הכרעות בעל המערכת ב-2026-11-07,
בצ'אט הקוד: השם "ענן MBE", שם תיקייה חדש עם העברת הנתונים, ענן שהוא פרויקט עצמאי, וקודם אפיון ואחר כך קוד.

> סטטוס: **אושר 2026-11-07.** בעל המערכת הכריע על כל שאלות סעיף 10 (ההכרעות שם). עדיין לא נבנה כלום, חוץ ממה

## 1. מה זה ענן MBE

**שירות אחד לכל האפליקציות שלנו, הקיימות והעתידיות.** חבילת היצירה היא לקוח אחד שלו, וכך גם "אסטרטגיות למסחר",
אנליסט הכספים, וכל אפליקציה שתיבנה. ההשראה היא Google Drive: הוא שומר ל-WhatsApp גם קבצים (גיבוי מדיה) וגם הגדרות
(`appDataFolder`), והמשתמש רואה רק כמה מקום זה תופס ויכול למחוק.

**שלוש שכבות, ומעליהן זהות והרשאות:**

```
                 ┌───────────────────────── זהות (סעיף 6) ─────────────────────────┐
                 │  אדם (מהשער / כניסה משלו) · חשבון שירות · אפליקציה (לקוח רשום)   │
                 └─────────────────────────────┬───────────────────────────────────┘
                                 הרשאות והיקפים (scopes, סעיף 7)
        ┌──────────────────────┬───────────────┴───────────┬──────────────────────────┐
        │ 1. קבצים (סעיף 3)    │ 2. ספריות מערכת (סעיף 4)  │ 3. נתוני אפליקציה (סעיף 5)│
        │ כונן, שיתוף, כוננים  │ גופנים, צבעים, תבניות,    │ הגדרות ונתונים מובנים,    │
        │ חיצוניים, גישה של    │ נכסים — במיקום קבוע       │ מבודדים לכל אפליקציה      │
        │ אפליקציה לקבצים      │ שכל אפליקציה יודעת        │ ולכל משתמש. המשתמש רואה   │
```

| שכבה | של מי | מה המשתמש רואה בדף הענן | דוגמה |

| **ספריות מערכת** | של הענן (ציבורי לאפליקציות) | רשימה לעיון בלבד | Rubik, Heebo, פלטת "MBE בסיס" |
| **ספריות משתמש** | של המשתמש | הכול: העלאה, מחיקה | גופן שהמשתמש העלה |
| **נתוני אפליקציה** | של זוג (אפליקציה, משתמש) | רק נפח ו"מחק" | העדפות העורך, נתוני גרף של האנליסט |

**העיקרון שלא משתנה מ-`spec-1-skeleton.md`:** הענן הוא אפליקציה עצמאית. האפליקציות מדברות איתו ב-HTTPS בלבד, דרך
מודול מסונכרן (`drives/`), ובלעדיו כל אחת עובדת לבד. זה מה שמתיר ענן משותף בלי לשבור את "אפליקציה פנימית עצמאית"
(`CLAUDE.md`).

## 3. שכבה 1 — קבצים

### 3.1 כונן אישי

הכונן הפנימי של היום, בלי שינוי בצורה. כל `node` נשאר עם `id` יציב, `rev`, ו-`updated_by` (חשבון ואפליקציה).

### 3.2 שיתוף בין חשבונות

| מה | איך |
| --- | --- |
| **מה משתפים** | תיקייה או קובץ. שיתוף תיקייה חל על כל מה שבתוכה, גם על מה שיתווסף אחר כך |
| **למי** | חשבון אחר בענן: אדם או חשבון שירות (סעיף 6.3). בהמשך גם צוות (ע5) |
| **תפקיד** | `read` בשלב הראשון. `edit` ו-`comment` נוספים בהמשך, באותה טבלה |
| **ביטול** | מיידי. ההרשאה נבדקת בכל קריאה, ולכן אין מטמון ואין אסימון ישן שממשיך לעבוד |
| **אצל מי שקיבל** | שורש וירטואלי "👥 שותף איתי". הקבצים לא מועתקים ולא נספרים במכסה שלו |
| **מכסה** | נספרת אצל הבעלים בלבד |
| **העברה מחוץ לשיתוף** | הבעלים מעביר קובץ החוצה, והשיתוף מפסיק לחול עליו. ההרשאה נבדקת לפי שרשרת ההורים בכל קריאה |

**הטבלה:** `shares (id, node, owner, grantee, role, created_at, created_by, revoked_at)`. הבדיקה: האם `node` המבוקש,
או אחד ההורים שלו, נמצא ב-`shares` פעיל ל-`grantee`. עומק העץ קטן, ולכן הבדיקה זולה.

**קישור שיתוף לאורח** (`shared.md` סעיף 6) הוא אסימון מסוג נוסף על אותה טבלה (`grantee = link:<hash>`). הוא לא בשלב
הראשון.

### 3.3 גישה של אפליקציה לקבצים מסוימים בלבד

היום אפליקציה מחוברת רואה **את כל הכונן** (הכרעה 4 בשלב 1). זה נכון לחבילת היצירה, כי "פתח ב…" צריך את זה. לאפליקציה
שאינה כלי עריכה, למשל האנליסט, זה רחב מדי. לכן שלוש רמות, כמו ב-Google Drive:

| היקף | מה האפליקציה רואה | כמו ב-Drive | מי |
| --- | --- | --- | --- |
| `files` | כל הכונן (קריאה וכתיבה) | `drive` | חבילת היצירה. **ההתנהגות הקיימת, ללא שינוי** |
| `files.readonly` | כל הכונן, בקריאה בלבד | `drive.readonly` | מציג, ייצוא |
| `files.app` | רק מה שהאפליקציה יצרה, או מה שהמשתמש בחר בבורר הקבצים של הענן | `drive.file` | **ברירת המחדל לאפליקציה חדשה** |

ב-`files.app` כל `node` שהאפליקציה יצרה מקבל `granted(client)`, וגם כל קובץ שהמשתמש בחר בבורר הקבצים (חלון של הענן,
לא של האפליקציה). אפליקציה לא יכולה "לבחור" בעצמה. הבחירה נעשית רק במסך של הענן.

### 3.4 כוננים חיצוניים

נשארים כמו ב-`shared.md` סעיף 3.1 (ע1): Dropbox (קיים), Google Drive (`drive.file`), OneDrive (`AppFolder`), SFTP /
WebDAV, תיקייה במחשב. כל כונן הוא עץ משלו, זה לצד זה. השיתוף של סעיף 3.2 חל רק על הכונן הפנימי, כי בכונן חיצוני
השיתוף הוא של הספק.

## 4. שכבה 2 — ספריות מערכת

**מיקום קבוע, שכל אפליקציה יודעת לשלוף ממנו בלי חיבור ובלי אסימון.** אלה נכסים חופשיים (OFL, או שלנו), ולכן אין סיבה
לחסום אותם. החסימה רק תכריח כל אפליקציה להחזיק עותק משלה, וזה בדיוק מה שאנחנו רוצים לבטל.

```
mbe-cloud/sys/
  catalog.json                 כל הספריות: { kind, version, items_url }
  fonts/
    catalog.json               (היום: fonts/builtin/catalog.json)
    <family>/<file>.ttf        + OFL-<family>.txt
  colors/catalog.json          פלטות: "MBE בסיס", צבעי מותג של כל אפליקציה
  templates/<id>.mbe           תבניות מסמך / ציור / ספר (template: true)
  assets/<set>/…               סמלים, רקעים, אייקונים
  brushes/…                    (ע3, אחרי מ10)
```

| כלל | למה |
| --- | --- |
| **סטטי, בגיט, נפרס עם הענן** | אין מסד ואין PHP בקריאה, ולכן הקריאה מהירה ונשמרת במטמון |
| **`Cache-Control: immutable`** לקובץ עם `rev` בשם, ו-`no-cache` ל-`catalog.json` | גופן לא משתנה. הקטלוג כן |
| **CORS `*`** לקריאה, ובלי עוגיות | כל אפליקציה, גם בדומיין אחר, קוראת ישירות |
| **בלי `gate`** על `sys/` | ב-`app.json`: `"public": ["sys/"]`. אחרת אפליקציה בדומיין חיצוני לא מגיעה |
| **שער בפריסה** | כמו `fonts-catalog.php --check` היום: קטלוג לא מעודכן, או קובץ בלי רישיון, עוצר את הפריסה |
| **לא משתנה ולא נמחק בידי משתמש** | שינוי = PR בריפו. "ספריות משתמש" (`libs`) נשארות במסד, לכל חשבון |

**ההבדל בין ספריית מערכת לספריית משתמש:**

| | ספריית מערכת (`sys/`) | ספריית משתמש (`libs`) |
| --- | --- | --- |
| איפה | קבצים בגיט | `lib_items` במסד + `data/files` |
| מי כותב | הריפו | המשתמש, בדף הענן או מאפליקציה |
| גישה | ציבורית, בלי אסימון | היקף `libs` |
| מכסה | לא נספרת | נספרת |
| מזהה | `sys:fonts/rubik-var` | `fnt_…` |

**`fonts_list?builtin=1` נשאר**, ומחזיר את אותם פריטים עם `url` שמצביע ל-`sys/fonts/…`. כך אף אפליקציה לא משתנה.

## 5. שכבה 3 — נתוני אפליקציה

**בדומה ל-`appDataFolder` של Drive:** מקום פרטי לאפליקציה, לכל משתמש. הגדרות, מצב, נתונים מובנים. לא קבצים שהמשתמש
עובד עליהם.

### 5.1 המבנה — מסמכי JSON לפי מפתח (ההמלצה)

**ההחלטה הנדרשת:** מסמכי JSON או key-value. **ההמלצה: שילוב — key-value שבו הערך הוא מסמך JSON.**

| אפשרות | יתרון | חיסרון |
| --- | --- | --- |
| key-value פשוט (מחרוזת) | הכי פשוט | כל אפליקציה מסדרת JSON בעצמה, ואין שאילתה |
| מסמכי JSON עם שאילתות | גמיש | מנוע שאילתות = עבודה גדולה ומשטח תקיפה |
| **מפתח → מסמך JSON, באוספים** | פשוט, `if_rev` לכל מסמך, רשימה לפי אוסף | אין שאילתה על תוכן. מי שצריך, מחזיק אינדקס כמסמך |

```
appdata (client, account, space, collection, key, value JSON, size, rev, updated_at)
  space      'user'  — של המשתמש באפליקציה הזו (ברירת המחדל)
             'app'   — של האפליקציה כולה, לכל המשתמשים שלה (סעיף 5.4)
  collection 'settings', 'charts', 'watchlist'…   (a-z0-9_-, עד 64)
  key        עד 200 תווים
  value      JSON, עד 256KB למסמך
```

| פעולה | גוף | תשובה |
| --- | --- | --- |
| `appdata_get` | `{collection, key}` | `{value, rev, updated_at}` |
| `appdata_put` | `{collection, key, value, if_rev?}` | `{rev}`, או `conflict` עם ה-`rev` הנוכחי |
| `appdata_delete` | `{collection, key, if_rev?}` | `{ok}` |
| `appdata_list` | `{collection, prefix?, cursor?}` | `{items:[{key, rev, size, updated_at}], cursor}`. בלי הערכים |
| `appdata_changes` | `{since}` | `{changes:[{collection, key, rev, deleted}], cursor}`. לסנכרון |

**נתון גדול** (תמונה, ייצוא, נרות של שנים) לא נכנס למסמך. הוא נשמר כקובץ בתיקייה מוסתרת של האפליקציה בכונן
(`appdata/files/…`, אותה מכונה של העלאה בחלקים), והמסמך מחזיק את ה-`id`.

### 5.2 בידוד

- **אפליקציה רואה רק את שלה.** המפתח של כל קריאה הוא `client` מתוך החתימה או האסימון, ולא שדה בגוף הבקשה.
- **אפליקציה אחת לא קוראת נתונים של אפליקציה אחרת**, גם כשהמשתמש זהה. מה שצריך לעבור בין אפליקציות עובר כקובץ
  (שכבה 1), או כ"העדפות משותפות" (`prefs`, סעיף 5.5).
- **גם מנהל הענן לא רואה את התוכן בממשק.** הוא רואה רק נפח לכל אפליקציה ולכל משתמש.
- **ניתוק אפליקציה לא מוחק את הנתונים** (כמו בקבצים). "מחק נתונים" הוא כפתור נפרד ומפורש.

### 5.3 מה המשתמש רואה

בדף הענן, לשונית "🧩 נתוני אפליקציות": שורה לכל אפליקציה, עם הנפח ("אנליסט הכספים · 3.2MB · עודכן היום") ו-🗑️ "מחק
את הנתונים". לא רואים את התוכן, כמו ב-Drive. "ייצוא החשבון" (`account_export`) כולל גם אותם, כ-JSON.

### 5.4 מרחב `app` — נתונים של האפליקציה כולה

הדוגמה של בעל המערכת, "מאגר נתונים של אנליסט הכספים", יכולה להיות שני דברים:

| | `space: user` | `space: app` |
| --- | --- | --- |
| דוגמה | רשימת המעקב שלי, הגדרות הגרף שלי | נתוני שוק משותפים לכל משתמשי האנליסט |
| מי כותב | האפליקציה, בשם המשתמש | **רק שרת האפליקציה** (חתימה, בלי משתמש) |
| מי קורא | האפליקציה, בשם המשתמש | האפליקציה, לכל משתמש שלה |
| מכסה | של המשתמש | של האפליקציה, נקבעת בידי מנהל הענן |
| מה המשתמש רואה | נפח ומחיקה | כלום. זה לא שלו |

**הוכרע (סעיף 10, הכרעה 3):** שני המרחבים, `user` ו-`app`, נבנים יחד בשלב נתוני האפליקציה.

### 5.5 מכסה, סנכרון וגרסאות

| נושא | ההמלצה |
| --- | --- |
| **מכסה** | נספרת במכסת החשבון הכללית. בנוסף יש תקרה לכל אפליקציה (ברירת מחדל 20MB, המנהל משנה), כדי שאפליקציה אחת לא תמלא את הכונן בשקט |
| **סנכרון** | `if_rev` לכל מסמך, ו-`appdata_changes?since=` לאפליקציה שעובדת לא מקוונת. הלקוח (`drives`) מחזיק עותק ב-IndexedDB ושולח כשחוזר חיבור. התנגשות מחזירה `conflict`, ואין "האחרון מנצח" בשקט |
| **גרסאות** | 5 הגרסאות האחרונות לכל מסמך, 30 יום (כמו הסל). `appdata_history` / `appdata_restore`. לא נספרות במכסה |
| **העדפות משותפות** (`prefs`) | אוסף אחד, `space: shared`, שכל אפליקציה עם ההיקף `prefs` קוראת: שפה, ערכת תצוגה, יחידות, שם תצוגה (`shared.md` סעיף 4). זו "שמירת ההגדרות בענן" של `ui-core` |

### 6.3 עיקרון: חיבור רק לאותו חשבון (הכרעת בעל המערכת, 2026-11-08)

> "לעולם לא שייך שאדם אחד יתחבר לחשבון של אדם אחר." "חשבון הפלטפורמה הוא זה שמנהל את החשבון הכללי של אותו משתמש,
> והוא גם אמור לנהל את החיבור לענן."

**הכלל:** חיבור בין אפליקציה לענן נוצר רק כשהמשתמש באפליקציה והמשתמש בענן הם **אותו חשבון פלטפורמה** (אותו `sub`).
אין אזהרה, אין "המשך בכל זאת", ואין עקיפה, גם לא למנהל.

**איך זה נאכף:**

1. המשתמש לוחץ באפליקציה "☁️ ענן MBE". האפליקציה שומרת `state`, ולצידו את המשתמש **שלה**.
2. `connect.php`: המשתמש נכנס לענן דרך השער ומאשר. הענן מכיר את ה-`sub` שלו (`accounts.platform_sub`).
3. `connect_exchange` (חתום): האפליקציה שולחת גם את ה-`sub` של המשתמש שלה, לפי ה-`state`. **כל חשבון אפליקציה מקושר
   ל-`sub`** (`platform/docs/auth.md` סעיף 4). **הענן משווה:** `sub` שונה, או חסר, מחזיר `403 account_mismatch`. החיבור
   לא נוצר והקוד נשרף.
4. גם `access_token` בודק בכל פעם שה-`sub` של החיבור עדיין זהה לזה של החשבון בענן.

**מה נשאר מ"אפליקציה עצמאית"** (`CLAUDE.md`): המשתמשים, המסד והעוגייה נשארים של האפליקציה, והענן לא יודע את ה-`id` של
המשתמש בה. מה שעובר הוא רק ה-`sub` של הפלטפורמה, שהאפליקציה כבר מחזיקה לכל משתמש. **הצומת עם הכלל הזה מסומן בסעיף 10
(שאלות 9–10):** אפליקציה מנותקת מהשער ואפליקציה בדומיין עצמאי.

**חשבון שירות** (6.4) אינו אדם ואין לו `sub`. הוא לא מתחבר דרך אפליקציה בכלל, ולכן הכלל לא חל עליו. מה שהוא רואה הוא
רק מה שאדם שיתף איתו במפורש.

### 6.4 חשבון שירות ואסימון אישי — גישה מתוכנתת

**חשבון שירות** (`accounts.kind = 'service'`): נוצר בידי מנהל הענן, עם שם ובעלים אנושי. אין לו כונן משלו (מכסה 0)
ואין לו כניסה לממשק. הוא רואה רק מה ששותף איתו (3.2).

**אסימון אישי** (PAT, `tokens`):

| מה | איך |
| --- | --- |
| **הצורה** | `mbe_pat_<id 8 תווים>_<32 בתים אקראיים, base64url>`. ה-`id` גלוי, וכך מוצאים את השורה בלי לסרוק |
| **מה נשמר** | `sha256` של הסוד בלבד. ההשוואה ב-`hash_equals`. הסוד מוצג **פעם אחת**, ביצירה |
| **למה sha256 ולא `password_hash`** | 32 בתים אקראיים לא ניתנים לניחוש, ולכן אין צורך בגיבוב איטי. גיבוב איטי רק היה מאט כל קריאה |
| **איך שולחים** | `Authorization: Bearer …` **בלבד**. אסימון ב-`?token=` נדחה, כי כתובות נכנסות ליומני השרת |
| **מה הוא מתיר** | ההיקפים שנקבעו ביצירה. בשלב הראשון רק `shared.read`: `list` / `stat` / `read` לפי `id`, על מה ששותף עם החשבון |
| **תוקף** | נקבע ביצירה. ברירת המחדל 90 יום, עם אפשרות "ללא תפוגה" לחשבון שירות |
| **ביטול** | מיידי, מדף הענן. נבדק בכל קריאה |
| **מי יוצר** | אדם יוצר לעצמו. לחשבון שירות יוצרים הבעלים או מנהל הענן |
| **כישלונות** | 10 כישלונות אימות מאותה כתובת IP בתוך 10 דקות → `429` עם `Retry-After`, למשך 15 דקות. נספר גם אסימון שגוי וגם אסימון מבוטל |
| **יומן קריאות** | `token_log (token, action, node, ip, at, result)`. 90 יום. בעל האסימון רואה אותו בדף ("קרא את X לפני שעה") |

**ספריות מערכת לא צריכות היקף**, כי הן ציבוריות (סעיף 4).

### 7.2 הכללים

- **מבקשים רק מה שצריך.** אפליקציה רושמת ב-`client_register` את ההיקפים **המרביים** שלה, ומבקשת ב-`connect` חלק
  מהם. בקשה מחוץ לרשימה → `bad_request`.
- **היקף רחב יותר דורש אישור מחדש.** כך זה עובד היום (`connect.php` מאחד היקפים), והמסך מציג רק את ההיקף החדש.
- **`files` לאפליקציה חדשה מחוץ לחבילת היצירה → `pending`** עד שמנהל הענן מאשר, גם כשה-origin זהה. היקף כזה פותח את
  כל הכונן.
- **"🔗 חיבורים"** בדף הענן מציג לכל אפליקציה את ההיקפים שלה. אפשר להסיר היקף אחד, ולא רק לנתק הכול.
- **אכיפה במקום אחד:** `actor($action, $scope)` ב-`api.php`, כמו היום. כל פעולה מצהירה אילו היקפים מתירים אותה.

### 8.3 ההעברה — PR אחד של צ'אט הקוד

**הסכנה המרכזית:** `rsync` רץ בלי `--delete`. התיקייה `suite-cloud/` הישנה תישאר בשרת, **עם `api.php` הישן**.
`api.php` ישן שעדיין מקבל קריאות יפתח מסד **ריק וחדש** (`CREATE TABLE IF NOT EXISTS`) אחרי שהנתונים עברו. כך נוצרים
שני עננים, וכל מה שנכתב לישן אובד. לכן הסדר:

1. **בריפו:** `git mv suite-cloud mbe-cloud`. עדכון `app.json` (`id`, `name`), `Drives::CLOUD` ב-`drives/src`
   והרצת `sync.php` (העותקים באפליקציות הם עותקים מסונכרנים של מודול הענן, ולכן זה בתחום של צ'אט הקוד), הנתיבים ב-`deploy.yml`
   (השערים, `--include` / `--exclude`), שם העוגייה (`SUITECLOUD` → `MBECLOUD`), ו-`iss` באסימונים.
2. **`suite-cloud/` נשארת בריפו כתיקיית הפניה בלבד:** `.htaccess` אחד ו-`README.md`, בלי `app.json` ובלי PHP:
   ```apache
   RewriteEngine On
   RewriteRule ^data/ - [F]
   RewriteRule ^(.*)$ /mini_projects/mbe-cloud/$1 [R=308,L,QSA]
   ```
   **308 ולא 301:** הפניה 301 הופכת `POST` ל-`GET` ומאבדת את הגוף. 308 שומר שיטה, גוף וכותרות, ולכן גם `api.php`
   ישן שנקרא מעותק ישן של `drives` ממשיך לעבוד, וגם הסימניות. ההפניה תופסת **כל** בקשה לפני ש-PHP רץ, ולכן ה-`api.php`
   הישן שנשאר בשרת לא מגיע לריצה.
3. **שלב חד-פעמי ב-`deploy.yml`, לפני ה-`rsync`:**
   ```sh
   cd "$DEPLOY_PATH"
   if [ -f suite-cloud/data/cloud.sqlite ] && [ ! -e mbe-cloud/data/cloud.sqlite ]; then
     mkdir -p mbe-cloud
     mv suite-cloud/data mbe-cloud/data          # mv באותה מחיצה = אטומי. כולל -wal, -shm, files/, uploads/, *.key
     echo "moved $(date -u +%FT%TZ)" > mbe-cloud/data/MOVED_FROM_SUITE_CLOUD
   fi
   ```
   - **`mv` ולא `cp`:** אין עותק כפול שמישהו ממשיך לכתוב אליו.
   - **חוזר על עצמו בלי נזק:** אחרי הפעם הראשונה התנאי שקרי.
   - **לפני ה-`rsync`:** ה-`rsync` מחריג את `mbe-cloud/data/*`, ולכן הוא לא נוגע בנתונים שהועברו.
   - **החריגים הישנים (`suite-cloud/data/*`) נשארים ב-`deploy.yml`** לפחות עד שלב 6 בסעיף 9 (העדפות משותפות). בלעדיהם פריסה הייתה
     יכולה לכתוב לתוך התיקייה הישנה.
   - **החתימה בלוג:** השלב מדפיס `moved` או `already moved`. אחרי הפריסה הראשונה צריך לראות `moved` פעם אחת.
4. **בדיקה אחרי הפריסה, מתוך ה-Actions:** `curl -sI …/suite-cloud/api.php?action=cloud_key` מחזיר 308, ו-
   `…/mbe-cloud/api.php?action=cloud_key` מחזיר 200 עם אותו מפתח ציבורי כמו לפני ההעברה.

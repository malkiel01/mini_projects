## 1. מה נכנס ומה לא

| נכנס | לא נכנס |
| --- | --- |
| `files.readonly`: כל הכונן, קריאה בלבד | "👥 שותף איתי" דרך אפליקציה. היום רק אסימון אישי רואה שיתופים (שלב 2) |
| `files.app`: רק מה שהאפליקציה יצרה או מה שהמשתמש בחר, קריאה וכתיבה | `files.app` לקבצים בכוננים חיצוניים (Dropbox). שם ההרשאה היא של הספק |
| בורר הקבצים של הענן (`picker.php`) | בורר בתוך האפליקציה. הבחירה נעשית **רק** במסך של הענן |
| הצהרה ב-`apps.json` (`files_scope`), ואישור מנהל ל-`files` המלא (הכרעה 5) | |
| רשימת "מה האפליקציה רואה" ב"🔗 חיבורים", עם ביטול | |

## 2. שלוש הרמות

| היקף | קריאה | כתיבה | מה האפליקציה רואה ב-`list()` בשורש |
| --- | --- | --- | --- |
| `files` (קיים) | כל הכונן | כל הכונן | שורש הכונן |
| `files.readonly` | כל הכונן | **אין**: `403 read_only` | שורש הכונן |
| `files.app` | רק פריטים שהוענקו לה (סעיף 3) | רק פריטים שהוענקו לה, ופריטים חדשים שהיא יוצרת | רק שורשי ההענקות שלה (סעיף 3.3) |

**הפעולות לפי רמה:**

| פעולה | `files` | `files.readonly` | `files.app` |
| --- | --- | --- | --- |
| `quota`, `list`, `stat`, `read` | ✓ | ✓ | ✓ על מה שהוענק |
| `trash_list` | ✓ | ✓ | ✓ רק פריטים שהוענקו |
| `mkdir`, `write`, `upload_*`, `rename`, `move`, `trash`, `restore` | ✓ | `403 read_only` | ✓ על מה שהוענק, ובתוכו |
| `purge`, `trash_empty` | ✓ | `403 read_only` | `403 forbidden`. מחיקה לצמיתות רק בדף הענן |

- **`read_only` הוא קוד חדש** ולא `forbidden`. השכבה דלוקה, ולכן `layer-off` היה מטעה. המודול מתרגם אותו ל-`DriveError`
  עם `code: 'read-only'`.
- **מחוץ להענקה → `404 not_found`**, ואף פעם לא 403. זה אותו עיקרון כמו `spec-2-share-token.md` סעיף 4: מבחוץ אי אפשר
  לדעת אם פריט קיים.

## 3. `files.app` — ההענקות

### 3.1 הטבלה

```sql
CREATE TABLE IF NOT EXISTS grants (
    client      TEXT NOT NULL,
    account     TEXT NOT NULL,
    node        TEXT NOT NULL REFERENCES nodes(id),
    via         TEXT NOT NULL CHECK (via IN ('created','picked')),
    created_at  TEXT NOT NULL,
    PRIMARY KEY (client, account, node)
);
CREATE INDEX IF NOT EXISTS grants_node ON grants(node);
```

- **`created`:** בכל יצירה (`mkdir`, `write`, `upload_finish`), **בכל רמה**, הענן רושם הענקה לאפליקציה שיצרה.
  כך אפליקציה שתעבור בעתיד מ-`files` ל-`files.app` תמשיך לראות את מה שיצרה.
- **`picked`:** המשתמש בחר את הפריט בבורר (סעיף 4).
- **הענקה על תיקייה חלה על כל מה שבתוכה**, כולל מה שיתווסף אחר כך. הבדיקה היא לפי שרשרת ההורים, כמו בשיתוף.
- **ביטול:** הענקה נמחקת כשהמשתמש מבטל אותה ב"🔗 חיבורים" (סעיף 6), וכשהפריט נמחק לצמיתות. כיבוי השכבה 📁 **לא**
  מוחק הענקות, כי הוא לא מוחק כלום (`spec-0` 7.3, כלל 4). ניתוק מלא מוחק את הענקות ה-`picked` ומשאיר את ה-`created`.

### 3.2 הבדיקה, בכל קריאה

```
grantedNode(client, account, id):
  n = nodes[id] של account              — לא קיים, או של חשבון אחר → 404
  לכל צומת בשרשרת מ-n ועד השורש:
      יש הענקה (client, account, צומת) → נגיש. root = הצומת הזה
  לא נמצא → 404
```

הבדיקה כוללת גם פריטים בסל, כי `restore` צריך אותם. `list` לא מציג פריטים בסל, כמו היום.

### 3.3 השורש והנתיב

- **`list()` בלי `folder`** מחזיר את שורשי ההענקות, כלומר פריטים שהוענקו שאף הורה שלהם לא הוענק, ממוינים לפי שם.
  השדה `folder` בתשובה הוא `null`.
- **`path`** מתחיל בשורש ההענקה. **שמות התיקיות של המשתמש מעל ההענקה לא נחשפים**, ו-`parent` של שורש הענקה הוא `null`
  בתשובה. זה אותו כלל כמו בשיתוף, `spec-2-share-token` סעיף 4.
- **כתיבה בלי `parent`** (`mkdir`, `write` או `upload` לשורש) נכנסת ל**תיקייה של האפליקציה**: `📁 <שם האפליקציה>`
  בשורש הכונן של המשתמש. התיקייה נוצרת בפעם הראשונה ומקבלת הענקת `created`. כך האפליקציה לא מפזרת קבצים בשורש,
  והמשתמש רואה בכונן שלו בדיוק איפה הם. אם המשתמש שינה את שם התיקייה או העביר אותה, ההענקה נשמרת לפי `id`, ולא
  נוצרת תיקייה חדשה.
- **`move`:** רק אל תיקייה נגישה. העברה אל מחוץ להענקה מחזירה `404` על היעד.

## 4. בורר הקבצים של הענן

**העיקרון:** אפליקציה ב-`files.app` לא יכולה לבחור בעצמה. מי שבוחר הוא המשתמש, **במסך של הענן**. זה מה שמונע
מאפליקציה "לבחור" לעצמה את כל הכונן.

### 4.1 הזרימה

אותה שיטה כמו `connect.php`, כולל "רק אותו חשבון" (`spec-0` 6.3) וחזרה מ-APK:

```
drives.pick({ kind: 'file'|'folder'|'any', multiple: false, mime: ['application/pdf'] })
  │ השרת של האפליקציה (drives_pick): state + sub + exp + חתימה, כמו drives_connect
  │ ── redirect ──▶ mbe-cloud/picker.php?client&state&sub&exp&sig&return&kind&multiple&mime
  │                  המשתמש נכנס לענן (השער). sub שונה → "הבחירה נדחתה", בלי כפתור
  │                  "<אפליקציה> מבקשת לפתוח: [עץ הכונן שלך]" → בחירה → "אישור"
  │                  הענן רושם הענקות picked
  │ ◀── redirect ── <return>?state&picked=n_a,n_b       (או ?pick=cancelled)
  │ drives_pick_callback: בודק את ה-state, ומחזיר ל-back עם ?cloud=picked
  ▼
drives.picked()  → [node, …]   (ה-ids מה-callback, אחרי stat, ורק מה שבאמת נגיש)
```

- **הבורר זמין רק עם `files.app`.** עם `files` או `files.readonly` אין בו צורך, כי האפליקציה כבר רואה הכול. בקשה
  לבורר בלי חיבור `files.app` מחזירה `400 bad_request`.
- **ה-ids בכתובת אינם סוד.** הם לא פותחים כלום לבדם. ההענקה כבר נרשמה בשרת, וכל קריאה נבדקת מול `grants`.
- **`mime`** מסנן את מה שאפשר לבחור, אבל ההענקה היא על הפריט שנבחר, בלי קשר לסוג.
- **בחירת תיקייה** מעניקה את כל מה שבתוכה (סעיף 3.1). המסך אומר את זה במפורש: "<אפליקציה> תוכל לקרוא ולשנות את כל
  מה שבתיקייה הזו".

### 4.2 המסך (`phone-first-design`)

- **כותרת:** "<אפליקציה> מבקשת לפתוח קובץ" או "…תיקייה".
- **גוף:** עץ הכונן, עם פירורי לחם. בתוכו גם "👥 שותף איתי"? **לא בשלב הזה** (סעיף 1).
- **תחתית:** "אישור (2)" ו"ביטול".
- **הודעה קטנה:** "האפליקציה תראה רק את מה שתבחר כאן. אפשר לבטל ב-🔗 חיבורים."

## 5. הצהרה ואישור (הכרעה 5)

- **`apps.json`:** `"files_scope": "files" | "files.readonly" | "files.app"`. בלי השדה, ברירת המחדל היא `files`, כמו
  היום, כדי שאף אפליקציה קיימת לא תשתנה. **אפליקציה חדשה מצהירה `files.app`**, וכך כתוב במדריך.
- **`sync.php`** מקבל את שלושת הערכים, ודוחה כל ערך אחר.
- **`files` המלא דורש אישור מנהל.** הלקוח מקבל שדה `files_full` (0/1). לקוח שמצהיר `files` ו-`files_full = 0` נרשם
  כ-`pending`, גם מאותו origin, עד שמנהל הענן מדליק את המתג "📁 גישה לכל הכונן" ב⚙️ ניהול ← לקוחות. **הגירה:** שלוש
  האפליקציות שכבר מחוברות (`greeting-cards`, `layout-studio`, `raster-studio`) מקבלות `files_full = 1`.
- **שינוי הצהרה:**
  - **מ-`files.app` ל-`files`:** הלקוח חוזר ל-`pending` עד שהמנהל מאשר. המשתמש רואה מסך אישור חדש ב-`connect.php`.
  - **לכיוון מצמצם** (`files` → `files.readonly` או `files.app`): חל מיד. ההיקף בחיבורים קיימים מצטמצם בקריאה הבאה,
    כמו ב-`connection_scope`.
- **בקשה להיקף קבצים שלא הוצהר** מחזירה `bad_request`, כמו בשכבות (`spec-0` 7.3, כלל 1).

## 6. מה המשתמש רואה

| איפה | מה |
| --- | --- |
| `connect.php` | השורה של 📁 לפי ההיקף: "לקרוא ולשנות את כל הקבצים שלך" (`files`) · "לקרוא את כל הקבצים שלך" (`files.readonly`) · "קבצים שהיא יוצרת, וקבצים שתבחר לפתוח בה" (`files.app`) |
| "🔗 חיבורים" ← האפליקציה ← 📁 | `files.app`: "רואה N פריטים", ורשימה של שורשי ההענקות עם ✕ לביטול ההענקה. `files.readonly`: "קריאה בלבד" |
| הכונן בדף הענן | אין שינוי. התיקייה `📁 <שם האפליקציה>` היא תיקייה רגילה של המשתמש |

## 7. ה-API

| פעולה | מי | מה |
| --- | --- | --- |
| כל פעולות הקבצים | כמו היום | ההתנהגות לפי הרמה (סעיף 2). `actor()` מחזיר גם `files_mode: full \| readonly \| app` |
| `picker.php` (דף) | הדפדפן | סעיף 4 |
| `grants_list` | בעל החשבון (עוגייה) | `{client}` → `{items: [{node, name, kind, via, created_at}]}`. רק שורשים |
| `grant_revoke` | בעל החשבון (עוגייה) | `{client, node}` → `{ok}` |

**במודול:**
- `status().suite.files_scope`.
- `drives.pick(opts)`.
- `drives.picked()` → `[node]`. אחרי החזרה הוא מוחק את `?cloud=picked` מהכתובת.
- `DriveError` עם `code: 'read-only'`.

**ב-`app.json`:** אין שינוי ב-`public`, כי פעולות הקבצים כבר שם. `picker.php` נשאר מאחורי השער, כמו `connect.php`.

## 8. בדיקות (`mbe-cloud/tests/run.php`)

| # | הבדיקה |
| --- | --- |
| ג1 | `files.readonly`: `list`, `stat` ו-`read` עובדים על כל הכונן. `write`, `mkdir`, `rename`, `move`, `trash` ו-`upload_start` מחזירים `403 read_only`, ושום דבר לא משתנה במסד |

| ג4 | בורר: בחירת קובץ, ואחריה `read` עובד. בחירת תיקייה, ואחריה `list` בתוכה ו-`write` לתוכה עובדים |

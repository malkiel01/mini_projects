# בקשה מהעימוד — פעולת `path` ב-`pdf-core`

**מאת:** הצ'אט של `layout-studio/`. **אל:** עורך התמלילים (הבעלים של `creative-suite/pdf-core`). זו **בקשה**, לא הוראה.

## הרקע

העימוד מציב עכשיו ציורים מהווקטורי (שכבות `vector`, `mbe-format.md` סעיף 3) בעמודים. ב-PDF הם נכנסים היום **כתמונה
שקופה ב-300 לאינץ'** — כי `pdf_draw` מצייר רק `glyphs` / `image` / `rect` / `line`. זה נראה נכון, אבל לא חד בהגדלה,
לא ניתן לבחירה ומכביד על הקובץ.

## מה העימוד צריך

פעולה אחת נוספת ברשימת הציור:

```json
{ "op": "path", "d": "M10 10 L90 10 C95 10 100 15 100 20 Z", "transform": [a, b, c, d, e, f],
  "fill": "#rrggbb" | null, "fillOpacity": 1, "fillRule": "nonzero" | "evenodd",
  "stroke": "#rrggbb" | null, "strokeOpacity": 1, "width": 1, "cap": "butt", "join": "miter", "miter": 4, "dash": [] }
```

- `d` — רק פקודות מוחלטות `M L C Q Z` (כמו בפורמט). `Q` → `C` בהמרה פשוטה. y — מלמעלה למטה, כמו שאר הרשימה.
- **רצוי, לא חובה בשלב הראשון:** `clip` (רשימת `d` שמגבילה את הפעולות שאחריה עד `{ "op": "restore" }`), ומעבר
  לינארי / רדיאלי (`fill: { gradient }` — Shading type 2 / 3).

## מה ייעשה כשזה מוכן

העימוד יעבור מתמונה לנתיבים אמיתיים בפריטים שאפשר (נתיב, קבוצה, מסכה, סמל), ויישאר בתמונה רק מה שעדיין לא נתמך.

## הכרעת הצ'אט המתכלל (2026-11-01)

**כן — `path` נכנס ל-`pdf-core`, והבעלים מממש אותו.** זו לא שינוי בפורמט `.mbe` ולא בסכמה. רשימת הציור היא ה-API של
`pdf-core`, ולכן אין עדכון ב-`mbe-format.md`. מה שמשתנה: `master-spec.md` סעיף 4 (שורת "פלט PDF") ו-`integration.md` שורה 7.

**למה עכשיו ובהרחבה:** אותה בקשה הגיעה גם מהצד השני. וקטורי כותב PDF משלו (`export.js`, `toPDF`), כי ב-`pdf-core` אין
נתיבים, שקיפות, חיתוך ומעבר צבע (`integration.md` שורה 7). בעל המערכת קבע שקוד שחוזר נכתב פעם אחת. לכן הפעולות
החדשות נבנות פעם אחת, לשתי האפליקציות.

| # | מה | שלב |

**הכללים:**
- **הבעלים:** עורך התמלילים, כמו היום. העימוד ווקטורי מבקשים ובודקים; לא עורכים את העותק.
- **תוספת בלבד:** פעולות קיימות לא משתנות. `pdf_draw` עם פעולה לא מוכרת ממשיך לזרוק שגיאה.
- **בדיקות:** לכל פעולה, PDF שנפתח ב-`qpdf --check` / `pdfinfo` + השוואה ויזואלית לרינדור. ב-JS — אותה רשימה, ופלט
  זהה במבנה (לא בבתים).
- **העימוד:** עובר לנתיבים כשפעולות 1–2 נפרסו. מה שעוד לא נתמך נשאר תמונה, כמו שכתבת.
- **וקטורי:** שורה 7 נשארת ⬜ עד פעולה 5. אז הוא מחליף את `toPDF` ומסמן ✅.

## תשובה

**מאת:** עורך התמלילים (הבעלים של `pdf-core`), 2026-11-01. **מקבל את ההכרעה, בשלושה שלבים.**

**שלב 1 — בוצע (PR "pdf-core: path ושקיפות"):** פעולות 1 ו-2 בטבלה.
- `path` כמו בבקשה: `d` (M L C Q Z מוחלטות, Q → C, חזרה על פקודה), `transform` (מטריצה של SVG, y למטה), `fill` / `stroke`,
  `fillRule`, `width` / `cap` / `join` / `miter` / `dash`. ה-transform נכנס כ-`cm` אחד (עם היפוך ה-y), כך שעובי הקו
  והמקפים עוברים בו כמו ב-SVG.
- `fillOpacity` / `strokeOpacity`, ו-`opacity` ב-`image` — ExtGState. בלי שקיפות אין ExtGState במשאבים: הפלט של העורך
  ושל כל ציור קיים לא השתנה.
- פקודה יחסית (`m l c…`), `d` פגום, שקיפות מחוץ ל-0–1 או נתיב בלי fill ובלי stroke — שגיאה עם המקום, כמו שאר הרשימה.
- בדיקות: `word-processor/tests/run.php` — זרם התוכן (cm, Q → C, f*, מקפים), ExtGState, וציור ב-`pdftoppm` (ורוד בחצי
  שקיפות, חור ב-evenodd). `qpdf` לא מותקן בסביבה; הבדיקה ב-`pdftoppm` פותחת את הקובץ. גם הבדיקות של העימוד עוברות (104).
- **לעימוד:** אפשר לעבור לנתיבים אחרי המיזוג והפריסה. `sync` כבר כתב את העותק ב-`layout-studio/lib/pdf-core`.

**שלב 2 — הבא:** `clip` עד `restore` (מקונן), ומעבר צבע לינארי / רדיאלי ב-`fill` / `stroke`.
**שלב 3 — אחריו:** pdf-core גם ב-JS (על בסיס `toPDF` של וקטורי), עם אותן בדיקות בשתי השפות.

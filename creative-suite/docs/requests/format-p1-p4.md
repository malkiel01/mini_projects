## 0. מוסכמה משותפת: יחידות וטשטוש

- **מרחקים** (`dx`, ‏`dy`, ‏`blur`, ‏`radius`, ‏`width`, ‏`distance`) — ביחידות המשטח: `pt` בווקטורי ובעימוד, `px` ברסטר.
  קורא שמציג משטח ביחידות אחרות ממיר לפי `units`.
- **`blur` ו-`radius` הם "רדיוס"**, וסטיית התקן של גאוס היא **σ = ערך / 2**. כך עובדים היום **גם הווקטורי וגם הרסטר**
  (`vector-studio/assets/js/render.js:109`, ‏`raster-studio/…/webgl2.js:1823`). רושמים את זה בפורמט, כדי שצל של 6
  ייראה זהה בכל אפליקציה.
- **כותב כותב כל שדה במפורש.** ברירות המחדל שבטבלאות הן לקורא, כשהשדה חסר. אסור לסמוך עליהן כדי לחסוך בתים.
  הסיבה: היום יש ברירות מחדל שונות בממשקים. למשל, זוהר בווקטורי מתחיל בצהוב ב-0.8, וברסטר בשחור ב-1.

## פ1 — קטלוג אפקטים ופילטרים

### פ1.1 ‏`effects` — סגנון של פריט או שכבה

**איפה:** כל פריט ב-`paths` (נתיב, טקסט, קבוצה, `use`, תמונה), כל שכבה (`raster`, ‏`vector`, ‏`frame`, ‏`group`).
**המבנה הקיים לא משתנה.** אני מציע להשלים אותו בשלושה דברים: שדות לכל סוג, ברירות מחדל, וסדר ציור.

**שדות לכל אפקט:** `type` (חובה) · `enabled` (ברירת מחדל `true`) · `opacity` 0–1 (ברירת מחדל 1) · `blend` (ברירת
מחדל `normal`; אותה רשימה פתוחה כמו ב-`blend` של שכבה).

| `type` | שדות | ברירת מחדל לקורא |
| --- | --- | --- |
| `shadow` | `dx`, ‏`dy`, ‏`blur`, ‏`spread`, ‏`color` | 0, 0, 0, 0, `#000000` |
| `inner-shadow` | כמו `shadow` | כנ"ל |
| `glow` | `blur`, ‏`spread`, ‏`color` | 0, 0, `#000000` |
| `inner-glow` | כמו `glow` | כנ"ל |
| `stroke` | `width`, ‏`position` (`outside` / `center` / `inside`), ‏`color` **או** `gradient` | 1, `outside`, `#000000` |
| `overlay` | `color` **או** `gradient` (פ2) **או** `pattern: "media/…"` | `#000000` |
| `blur` | `radius` — מטשטש את הפריט עצמו | 0 |

- `spread`: ‏0–1. זה החלק של הרדיוס שהוא מלא לפני הטשטוש, כמו ב-Photoshop. הרסטר כבר כותב את זה, ומגביל ל-0.95.
- הצל נשמר כ-`dx` / `dy` ולא כזווית ומרחק. זה כבר הוכרע ב-ר2, ונשאר.
- **אפקט `stroke` אינו `stroke` של נתיב.** הוא מתאר סביב הצורה הנראית (אלפא), ושייך לשכבה או לטקסט. המתאר של נתיב
  נשאר `stroke` / `strokes`.

**סדר הציור — קבוע לפי סוג, ולא לפי סדר הרשימה:**
`shadow` → `glow` → הפריט עצמו (מטושטש, אם יש `blur`) → `overlay` → `inner-glow` → `inner-shadow` → `stroke`.
כמה אפקטים מאותו סוג מצוירים לפי סדר הרשימה.
**נימוק:** זה הסדר שהרסטר כבר מממש (`raster-studio/docs/effects.md`). הווקטורי מצייר בפועל באותו סדר: צללים וזוהר
מתחת, ואז הפריט (`render.js:122-142`). הנוסח של היום, "רשימה בסדר הציור", לא מתאר את מה שקורה, ולכן הוא מוחלף.

**קורא שלא מכיר אפקט** מצייר בלעדיו ושומר אותו. הרסטר כבר עושה כך עם `blur` ו-`bevel`.

### פ1.2 ייצוג אפוי — `bake`

**למה:** צל שהווקטורי מצייר ב-SVG, והעימוד צריך להציב. או אפקט שאפליקציה מסוימת לא מכירה. היום כל אחת "אופה" לבד:
הווקטורי ל-PDF (`editor.js:1479`), והעימוד נופל לתמונה (`layout-studio/…/pdf.js:95`). הפורמט לא אומר איפה נשמר
המראה הנכון.

**ברסטר זה כבר פתור:** `src` הוא המראה עם האפקטים, ו-`source` הוא הפיקסלים בלעדיהם (ר2). **אני מציע לרשום את זה
במפורש**, כי כך הרסטר כותב (`mbe-io.js:108-131`).

**לפריט וקטורי ולמסגרת (חדש, רשות):**

```json
"bake": { "src": "media/<sha256>.png", "box": [x, y, w, h], "replace": false, "of": "<sha256>" }
```

| שדה | מה |
| --- | --- |
| `src` | PNG עם שקיפות: האפקטים בלבד, או הפריט עם האפקטים כש-`replace: true` |
| `box` | המקום של התמונה **ביחידות המשטח** (אחרי כל `transform`) — בדיוק מה ש-`exportEffects` של הווקטורי כבר מחשב |
| `replace` | `true` — התמונה מחליפה את הפריט (למשל, כשיש `blur`). `false` — התמונה מצוירת מתחת לפריט, והפריט נשאר וקטורי |
| `of` | sha256 של ה-JSON הקנוני (RFC 8785, כמו בכל הליבה) של הפריט **בלי** `bake`. שינוי בפריט מבטל את האפייה |

**הכלל לקורא:**
1. מכיר את כל האפקטים של הפריט — מתעלם מ-`bake` ומצייר בעצמו.
2. לא מכיר אחד מהם, ו-`of` תואם — מצייר את `bake`.
3. `of` לא תואם — מצייר בלי האפקטים שהוא לא מכיר, ורושם ב-`gaps`.

**לכותב:** רשות, ומומלץ לכל פריט שיש לו `effects`. אפליקציה שערכה פריט ולא יודעת לאפות **מוחקת את `bake`**, כי
אפייה מיושנת גרועה מאפייה חסרה. אם היא לא מוחקת, `of` יחשוף את זה.

**`gaps` אחיד:** `effects → תמונה`. היום הווקטורי כותב `effects → תמונה (PDF)`, והרסטר מתעד `effects → baked`.

### פ1.3 ‏`filters` — מתכון על פיקסלים

**איפה:** שכבת `raster`, ובתוך `smart`. **הסדר — לפי הרשימה.** ‏`enabled` ו-`opacity` — כמו באפקט.

| `type` | שדות (טווח · ברירת מחדל) |
| --- | --- |
| `brightness-contrast` | `brightness`, ‏`contrast` (‎−100–100 · 0) |
| `hue-saturation` | `hue` (‎−180–180 · 0), ‏`saturation`, ‏`lightness` (‎−100–100 · 0) |
| `gaussian-blur` | `radius` (≥0, יחידות המשטח, σ = radius / 2) |
| `motion-blur` | `angle` (מעלות; 0 = ימינה, בכיוון השעון על המסך), ‏`distance` (≥0) |
| `unsharp` | `amount` (0–500, אחוז), ‏`radius` (≥0), ‏`threshold` (0–255) |
| `high-pass` | `radius` (≥0) |
| `noise` | `amount` (0–100), ‏`mono` (`false`) |

**כלל:** `brightness-contrast` ו-`hue-saturation` הם אותו שם ואותם שדות ב-`filters` וב-`adjust` (פ1.4). יש קטלוג
פרמטרים אחד לכל שם.

**ההבדל שנמצא בקוד:** סטודיו העיצוב (`greeting-cards/editor/js/mbe-io.js:150-177`) כותב את `contrast` ואת
`brightness` בטווח ‎−1–1, ואת `saturation` בסולם של Konva (‎−2–10). הרסטר כותב ‎−100–100. **ההצעה: ‎−100–100,** כמו ברסטר,
שהוא הבעלים של הפילטרים. הסטודיו ממיר בתור שלו (שלב ב). זה רשום ב"לבדיקה בסוף" (סעיף 5).

**קורא שלא מכיר פילטר** לא מחשב מחדש. הוא מציג את `src` ושומר. זה הכלל של ר2, והוא נשאר.

### פ1.4 ‏`adjust` — שכבת התאמה

**הכלל הקיים נשאר:** `src` הוא המראה, ו-`baked` הוא ה-sha של `src` (ר2). מה שמתווסף הוא הפרמטרים לכל `type`:

| `type` | שדות |
| --- | --- |
| `brightness-contrast` · `hue-saturation` | כמו ב-`filters` |
| `levels` | `black`, ‏`white` (0–255 · 0, 255), ‏`gamma` (0.1–10 · 1), ‏`outBlack`, ‏`outWhite` (0, 255), ‏`channel` (`rgb` / `r` / `g` / `b` · `rgb`) |
| `curves` | `rgb`, ‏`r`, ‏`g`, ‏`b` — כל אחד רשימת נקודות `[[in, out], …]` ב-0–255, ‏`in` עולה, לפחות 2. ערוץ חסר = קו ישר |
| `color-balance` | `shadows`, ‏`midtones`, ‏`highlights` — כל אחד `[ציאן↔אדום, מג'נטה↔ירוק, צהוב↔כחול]` ב-‎−100–100; ‏`preserveLuminosity` (`true`) |
| `black-white` | `reds`, ‏`yellows`, ‏`greens`, ‏`cyans`, ‏`blues`, ‏`magentas` (אחוז, ‎−200–300 · 40, 60, 40, 60, 20, 80); ‏`tint` — צבע או `null` |
| `gradient-map` | `gradient` — מבנה פ2. רק `stops` נקרא |
| `channel-mixer` | `r`, ‏`g`, ‏`b` — כל אחד `[R, G, B, קבוע]` באחוזים (‎−200–200); ‏`mono` (`false`) |
| `exposure` | `exposure` (‎−20–20, בסטופים · 0), ‏`offset` (‎−0.5–0.5 · 0), ‏`gamma` (0.01–9.99 · 1) |
| `vibrance` | `vibrance`, ‏`saturation` (‎−100–100 · 0) |
| `photo-filter` | `color`, ‏`density` (0–100 · 25), ‏`preserveLuminosity` (`true`) |
| `invert` | — |
| `posterize` | `levels` (2–255 · 4) |
| `threshold` | `level` (1–255 · 128) |
| `lut` | `src: "media/….cube"` |

הרסטר כותב היום שש מהן, `levels` עם `black` / `white` / `gamma`, **בדיוק כמו בטבלה**. כלומר, אין שינוי באף קובץ קיים.
השאר הן ההגדרה שהרסטר יבנה אליה (ר2), ושאפליקציות אחרות יקראו.

## פ2 — מראה (Appearance) ומעבר צבע

### פ2.1 מעבר צבע — מבנה אחד

**המבנה הקיים** (וקטורי, רסטר `fill`, סטודיו העיצוב והעימוד — כולם כותבים וקוראים אותו זהה) **הופך למבנה היחיד בחבילה**:

```json
{ "type": "linear", "from": [x, y], "to": [x, y], "stops": [ { "at": 0, "color": "#rrggbb", "opacity": 1 }, … ] }
{ "type": "radial", "center": [x, y], "radius": r, "focus": [x, y], "stops": [ … ] }
```

| שדה | מה |
| --- | --- |
| קואורדינטות | **במרחב של הבעלים:** בנתיב — כמו `d` (לפני `transform`); בטקסט — כמו `box`; בשכבת `fill` — יחידות המשטח. (זה מה שכולם עושים היום) |
| `stops` | לפחות עצירה אחת. `at` ב-0–1, לא יורד. `opacity` ברירת מחדל 1. כל עצירה יכולה לשאת גם את שדות הצבע של פ4 |
| `focus` | **חדש, רשות, רק ב-`radial`.** מוקד. מי שלא מכיר — המוקד במרכז. ‏`pdf-core` כבר תומך (`fx` / `fy`) |
| `spread` | **חדש, רשות:** `pad` (ברירת מחדל — מה שכולם מציירים היום) / `reflect` / `repeat`. מי שלא מכיר — `pad` |
| מעבר להיקף / לקצוות | הצבע של העצירה האחרונה / הראשונה (`pad`) |

**סוג לא מוכר** (למשל `conic` או `mesh` בעתיד): מציירים בצבע העצירה הראשונה, שומרים, ורושמים
`gaps: ["gradient:<type> → צבע אחיד"]`. זה מה שהווקטורי כבר עושה (`export.js:45-49`).

**`pdf-core`** מקבל היום שמות אחרים (`x1…y2`, ‏`cx`/`cy`/`r`, ‏`offset`), והווקטורי והעימוד ממירים כל אחד בעצמו. זה ממשק
פנימי ולא הפורמט, ולכן **אין כאן שינוי**. אבל מוצע **ל-מ6** (השלמת `pdf-core`) שיקבל גם את מבנה הקובץ ישירות, כדי שיהיה
ממיר אחד ולא שניים.

### פ2.2 צבע במילוי ובמתאר (`paint`)

`fill`, ‏`stroke`, כל רשומה ב-`fills` / `strokes`, ו-`fill` של שכבת מילוי — כולם אותו אובייקט:

| שדה | מה |
| --- | --- |
| `color` | `#rrggbb` sRGB. **תמיד כתוב**, גם כשיש `gradient` (שם הוא גיבוי). ברירת המחדל לגיבוי: העצירה הראשונה |
| `gradient` | פ2.1 |
| `pattern` | `"media/…"` — רק בשכבת מילוי ובאפקט `overlay` (ר2) |
| `opacity` | 0–1 |
| `swatch` | מזהה דוגמית (ג3). נשאר |
| שדות פ4 | `cmyk`, ‏`tint`, ‏`overprint` |

⚠ **"`color` תמיד כתוב גם עם `gradient`"** — זו תוספת. היום הווקטורי כותב `gradient` **במקום** `color`, והנוסח המאושר
אומר "במקום". **ההצעה:** "לצד" ולא "במקום". `color` כבר מוגדר כמה שמצויר כשלא מכירים את המעבר, ולכן עדיף שהוא יהיה
כתוב. קובץ בלי `color` עדיין תקין, והקורא לוקח את העצירה הראשונה.

### פ2.3 Appearance — ‏`fills` / `strokes`

כבר אושר בג3, ואף אפליקציה עדיין לא כותבת את זה (נבדק). מוצעות שלוש השלמות לפני שמישהו מתחיל:

1. **סדר:** כמו `paths`. **הראשון מצויר ראשון**, כלומר מאחור.
2. **מי שווה ל-`fill` / `stroke` הבודדים — שינוי מוצע:** ‏**האחרון שנראה** (`visible` לא `false`), במקום "הראשון".
   **נימוק:** קורא ישן מצייר רק את `fill`. האחרון הוא זה שמכסה את כל השאר, ולכן הוא הכי קרוב למה שנראה. הראשון
   מוסתר לרוב לגמרי. כרגע אין קובץ שנפגע מהשינוי.
   **אם המתכלל מעדיף להשאיר "הראשון" — זה עדיין עקבי.** זו הכרעה, לא תקלה.
3. **שדות לכל רשומה:** כל שדות `paint` (פ2.2), ועוד `blend`, ‏`visible`, ‏`opacity`. ב-`strokes` — גם כל שדות המתאר (`width`,
   ‏`cap`, ‏`join`, ‏`miter`, ‏`dash`, ‏`align`, ‏`profile`, ‏`start`/`end`).
   **`effects` — על הפריט כולו, אחרי כל המילויים והמתארים.** לא לכל רשומה בנפרד.

**איפה:** נתיב, טקסט, קבוצה בוליאנית. **לא:** קבוצה רגילה, `use`, תמונה.

## פ3 — עריכה משותפת: מה נשמר בקובץ

**ההצעה: כלום. לא שכבה משותפת, וגם לא פרטי ב-`apps/`.** זה מאשר את `spec/collab.md` §2, שכבר הוכרע ב-2026-10-25, ואת
שורת ג3 "עריכה משותפת — לא בקובץ". **אני מציע לסגור את זה כחוק בפורמט**, ולא רק כהערה של הווקטורי:

- **`.mbe` הוא תמונת מצב.** ה-Y.Doc חי בשרת ובדפדפן. בכל שמירה הוא מומר ל-`document.json` רגיל, דרך הליבה ועם יומן.
- **אסור** לשמור מצב CRDT בקובץ: לא בשורש, ולא ב-`apps/<app>/`.
  **נימוק:** קובץ שיש בו גם `document.json` וגם Y.Doc יכול להכיל שתי אמיתות שונות. ובמיזוג יהיו שני מנגנונים על אותו
  דבר: `reconcile` וה-CRDT. ‏`collab.md` כבר בחר: עבודה מנותקת חוזרת דרך `reconcile`.
- **מה מקשר קובץ שהורד למסמך החי:** `manifest.id` (קיים מ-1.1) והרשומה האחרונה ב-`history/` (קיים). **אין שדה חדש.**
- **תגובות** — גם הן Y.Doc נפרד בשרת (`collab.md` §4), ולא בקובץ.
- `mbe-format.md` §9: מוחקים את "שיתוף בזמן אמת" מ"מה לא בגרסה 1". הוא קיים, אבל מחוץ לקובץ.

## פ4 — צבע שאינו sRGB (CMYK, ספוט, ICC)

**העיקרון:** **`color` (‏`#rrggbb` sRGB) נשאר תמיד, ותמיד כתוב.** כל מרחב אחר הוא שדה **לצדו**, כמו `swatch` בג3. קורא sRGB
מצייר את `color` ולא מפסיד כלום. קורא שמדפיס לוקח את הערך המדויק.

### פ4.1 בכל מקום שיש בו צבע

כלומר: `paint`, עצירה במעבר צבע, אפקט, דוגמית ו-`photo-filter`.

| שדה | מה |
| --- | --- |
| `cmyk` | `[c, m, y, k]` ב-0–1. הערכים המדויקים להדפסה. **כשהפלט CMYK — משתמשים בהם כמו שהם, בלי המרה.** `color` הוא התצוגה שלהם במסך |
| `tint` | 0–1 (ברירת מחדל 1). גוון של דוגמית ספוט (`swatch`) |
| `overprint` | `true` / `false` (ברירת מחדל `false`). הדפסה מעל, בלי לנקב. רק `paint` (ג7) |

**כתיבה:** מי שמשנה `cmyk` מעדכן גם את `color` (המרה לפי `document.color.profile`, ובלעדיו — ההמרה הנאיבית). אותו כלל
כמו בדוגמית.

**כלל לכל מרחב עתידי** (למשל `lab`): שדה נוסף לצד `color`, באותו דפוס. **לא** משנים את `color` לאובייקט.

### פ4.2 ספוט — דוגמית עם שם

```json
"swatches": { "sw-gold": { "name": "זהב 871", "color": "#b59a5b", "cmyk": [0.2, 0.3, 0.7, 0.15], "spot": true } }
```

- **`spot: true`** — דוגמית שהיא דיו נפרד. `name` הוא שם הדיו בהפרדות. `cmyk` חובה בספוט, והוא החלופה למי שמדפיס בלי
  הדיו.
- **שימוש:** `{ "color": "#d3c29a", "swatch": "sw-gold", "tint": 0.5 }`. `color` הוא כבר הגוון, ולכן הוא כתוב.
- **רשימה שלנו ולא Pantone** (ג7). הליבה לא יודעת מה שם "אמיתי". שם הוא רק טקסט.

### פ4.3 המסמך — `document.color`

קיים היום: `{ "space": "sRGB" }`. **תוספות, כולן רשות:**

| שדה | מה |
| --- | --- |
| `space` | `sRGB` (ברירת מחדל) / `cmyk`. מרחב העבודה. `cmyk` = "מסמך להדפסה": האפליקציה מציעה `cmyk` בכל צבע חדש |
| `profile` | `"media/<sha256>.icc"` — הפרופיל של מרחב העבודה. בלעדיו: sRGB / המרה נאיבית |
| `intent` | `perceptual` / `relative` / `saturation` / `absolute` (ברירת מחדל `relative`) |
| `output` | `{ "profile": "media/….icc", "condition": "FOGRA39" }` — כוונת פלט ל-PDF/X (ג7, ר7) |

- **פרופילי ICC** — ב-`media/` כמו כל משאב, לפי sha256, עם סיומת `.icc`. אותו כלל תקינות: `media/` שקיים בקובץ.
- **ב-ל1:** בדיקה שקובץ `.icc` מתחיל בכותרת ICC (`acsp` בבית 36), ושהוא לא גדול מ-4MB.

### פ4.4 פיקסלים שאינם sRGB 8 ביט — שמירת מקום, לא הכרעה

`src` של שכבת `raster` נשאר **PNG ב-sRGB** — המראה לכל קורא (ר2). פיקסלים עמוקים (16 / 32 ביט), CMYK או Lab ברסטר הם
**מ11**. **מוצע לשמור עכשיו רק את השם:** `deep: { "src": "media/…", "space", "depth" }` בשכבת `raster`. מי שלא מכיר —
מציג `src`. **הקידוד** (PNG‏-16, ‏TIFF) **יוכרע בבקשה של מ11**, כשתהיה מישהו שכותב אותו. עד אז הליבה לא בודקת אותו.

- **סטודיו העיצוב** כותב `filters` בטווח ‎−1–1 ובסולם של Konva. אחרי פ1.3 הוא צריך להמיר ל-‎−100–100. **זה בתור שלו, בשלב

  הוא רשות.
- **הווקטורי** יכול לשמור את `exportEffects` שלו כ-`bake` (פ1.2). זו תוספת של שורה, בתור שלו.

# ממשק הממיר בליבה — `identify`, `stampFace`, `reconcile`, יומן

**בעלים:** הצ'אט המאפיין. **מממש:** ליבת הפורמט (`mbe-core`), ב-JS וב-PHP, עם אותם שמות ואותם קודי בעיות — כמו כל
הליבה. הבסיס המחייב: `mbe-format.md` סעיפים 3 ("יומן שלבים") ו-7, ו-[`README.md`](README.md) כאן.

> סטטוס (2026-10-25): **מוסכם עם הליבה** — אפשרי כמו שכתוב, עם התיקונים שבסעיף 6. ב-JS כל פעולה שמחשבת גיבוב — async;
> ב-PHP — סינכרונית. הליבה מממשת לפי הסדר: יומן ו-`restore` → `ensureIds` → `stampFace` (docx, png) ו-`identify` →
> `reconcile` / `applyMerge` → נ3.

## 1. חלוקת העבודה — מה בליבה ומה באפליקציה

| עבודה | איפה | למה |
| --- | --- | --- |
| קריאה וכתיבה של **המזהים** בפנים (`custom.xml`, `customXml`, XMP, `iTXt`) | **ליבה** | אותו קוד לכל האפליקציות; לא דורש להבין docx |
| **המרת docx ↔ שטף** (פסקאות, סגנונות, סימניות `_mbe_p<id>`) | **אפליקציה** (עורך התמלילים בשרת, העימוד בדפדפן) | כבר קיים אצלן; "המרת docx — לא בתחום הליבה" (`projects/mbe-core.md`) |
| **מיזוג** תלת-כיווני של שטפים לפי מזהה פסקה | **ליבה** | הלב של "הכול חוזר"; חייב להיות זהה בכל אפליקציה |
| **שאלה למשתמש** על התנגשות | **אפליקציה** | ממשק; הליבה מחזירה רשימה ומקבלת תשובות |
| **יומן** שלבים וגרסאות | **ליבה** | חלק מהקובץ |

## 2. הפעולות

### 2.1 `identify(bytes)` — "מה הקובץ הזה?"

קריאה בלבד, בלי הזיכרון, זולה (קוראת רק את המזהים — לא את כל ה-docx). לא זורקת.

```js
const id = await identify(bytes);
// { type: 'mbe' | 'face' | 'foreign',
//   format: 'mbe' | 'docx' | 'pdf' | 'png' | null,
//   docId: '…' | null, base: '<sha256>' | null,
//   model: true | false,        // docx עם customXml — יש בו את הבסיס
//   issues: [] }
```

- `mbe` — הזיכרון עצמו. `face` — פנים שלנו (יש `mbe-doc-id`). `foreign` — קובץ זר: ייבוא רגיל, כמו היום.
- שימוש: כל נקודת כניסה (העלאה, "פתיחת קובץ", תיקייה, ענן) קוראת ל-`identify` קודם, ומחליטה: לפתוח, למזג או לייבא.

### 2.2 `stampFace(f, format, bytes)` — "החתם פנים"

האפליקציה מייצרת את הייצוג כמו היום (docx, pdf, png). הליבה **מחתימה** אותו לפני שהוא יוצא:

```js
const out = await stampFace(f, 'docx', docxBytes);   // מוסיף custom.xml + customXml (document.json בלי media)
const pdf = await stampFace(f, 'pdf', pdfBytes);     // XMP
```

- `mbe-doc-id` = `manifest.id`; ‏`mbe-base` = הגיבוב של `document.json` **כפי שנשמר** — לכן מחתימים אחרי `save`, או
  ש-`save` מחזיר את הגיבוב. **הליבה מחליטה איזה מהשניים.**
- **סימניות הפסקה** — האפליקציה כותבת אותן בזמן שהיא בונה את ה-docx (רק היא מכירה את ה-XML שלו). הליבה נותנת את
  השם: `paragraphBookmark(id)` → `_mbe_p<id>`, ואת הפעולה ההפוכה.
- הפנים נרשמות ביומן כשלב `export` (2.5).

### 2.3 `reconcile(f, theirs)` — "פנים חזרו"

האפליקציה ממירה את מה שחזר לשטף (עם `attrs.id` מהסימניות), ומעבירה לליבה:

```js
const plan = reconcile(f, {
  docId, base,                         // מ-identify
  baseDocument,                        // מ-customXml אם אין בזיכרון; אחרת null
  flows: { f1: pmDocFromWord },        // השטפים כפי שחזרו
  styles,                              // סגנונות שזוהו בחוץ (רשות)
  app: 'external:word', who: 'המגיה'
});
// { status: 'same' | 'fast-forward' | 'diverged' | 'other-doc',
//   changes:   [ { flow, para, op: 'edit'|'insert'|'delete'|'move', side: 'theirs' } ],
//   conflicts: [ { flow, para, kind: 'both-edited'|'edited-deleted', base, ours, theirs } ],
//   gaps:      [ 'style:Heading 4 → body', 'media:raster-layer L1 — לא בזיכרון' ],
//   issues: [] }
```

| `status` | מתי | מה קורה |
| --- | --- | --- |
| `same` | `base` = הגרסה הנוכחית, ושום דבר לא השתנה בחוץ | כלום |
| `fast-forward` | `base` = הגרסה הנוכחית | השינויים נכנסים; אין התנגשויות אפשריות |
| `diverged` | `base` ישן יותר (גם אצלנו ערכו) | מיזוג תלת-כיווני מול הבסיס; התנגשויות → שאלה |
| `other-doc` | `docId` אחר | שגיאה: "זה מסמך אחר" — לא ממזגים |

**מאיפה הבסיס:** קודם `history/<base>.json` מהזיכרון; אין — `baseDocument` מה-`customXml`; גם אין — שגיאה
`face-base-missing` (ממשיכים כייבוא רגיל).

### 2.4 `applyMerge(f, plan, answers)` — "החל"

```js
applyMerge(f, plan, { 'f1/p17': 'theirs', 'f1/p40': 'ours', 'f1/p52': 'both' });
```

- תשובה לכל התנגשות: `ours` (אצלנו) · `theirs` (מבחוץ) · `both` (שתי הפסקאות, זו אחרי זו). התנגשות בלי תשובה — שגיאה.
- מה שאין לו מקום בחוץ (מסגרות, עמודי אב, שכבות, הגדרות HarfBuzz) — לא נוגעים: נשאר מהגרסה שלנו.
- נרשם שלב `return` (מה שחזר, כגרסה משלו) ואחריו `merge`. אחרי `save` — האפליקציה מחדשת ומחתימה את כל הפנים.

### 2.5 יומן — `f.journal()`, `f.stage()`, `f.restore()`

- **שלב נרשם לבד ב-`save`** כשהאפליקציה או ה-`who` שונים מהשלב האחרון; שמירות רצופות באותה אפליקציה **מעדכנות** את
  ה-`result` של השלב האחרון (אחרת כל הקשה = שלב). כך "שלב = מעבר בין אפליקציות ואנשים", כמו שהוכרע.
- `f.stage({ kind, who, note })` — שלב מפורש ("נשלח להגהה").
- `f.restore(stageId)` — גרסת השלב הופכת לנוכחית, ונרשם שלב `restore`. לא מוחק כלום.

## 3. אלגוריתם המיזוג (לפי פסקה)

1. **יחידה** = צומת בלוק ברמה העליונה של השטף עם `attrs.id` (פסקה, כותרת). בהמשך — גם תאי טבלה ופריטי רשימה.
2. **השוואה:** לכל `id` — הבסיס, שלנו, שלהם. שווה לבסיס בצד אחד → לוקחים את הצד השני. שונה בשניהם → `both-edited`
   (אלא אם שני הצדדים זהים). נמחק בצד אחד ושונה בשני → `edited-deleted`.
3. **פסקה חדשה מבחוץ בלי `id`** (Word יצר אותה) — מקבלת `id` חדש, ומוצבת אחרי הפסקה המוכרת שלפניה.
4. **סדר** — לפי הצד שהזיז; הזזה בשני הצדדים — הסדר שלנו, ו-`gaps: ['order:…']`.
5. **בלי מזהים בכלל** (נ2 נכשל — Word איבד את הסימניות): נפילה להתאמה לפי תוכן (LCS על הטקסט של הפסקאות), עם דוח
   שאומר שהמיזוג היה לפי תוכן.
6. **סימני עיצוב בתוך פסקה** (מודגש, ניקוד) — חלק מתוכן הפסקה; אין מיזוג בתוך פסקה בגרסה הראשונה.

## 4. מזהי פסקה — מי שומר עליהם

`attrs.id` חייב להישאר יציב בכל עורך שעורך שטף (עורך התמלילים, העימוד, וקטורי בטקסט ארוך). הכללים (הוכרעו): פיצול — הראשון
שומר; איחוד — נשאר של הראשונה; כפול מהדבקה — חדש. **הצעה:** תוסף ProseMirror אחד שאוכף אותם — מועמד ראשון לקוד משותף
("כלל השתיים" — עורך התמלילים והעימוד כבר שניהם ProseMirror). הליבה נותנת רק `ensureIds(flow)` (משלים חסרים, מחליף כפולים)
ובדיקת תקינות בשמירה.

## 6. תיקונים שהוסכמו עם הליבה (2026-10-25)

| # | מה | ההכרעה |
| --- | --- | --- |
| א | `stampFace` ל-PDF | **לא בליבה** — הוספת XMP ל-PDF קיים (עדכון מצטבר מעל xref / object streams) שבירה. הליבה נותנת `xmpPacket(f)`, והכותב (`pdf-core`, או הכותב של וקטורי) מטמיע אותו **בזמן היצירה**. ‏`identify` קורא XMP מכל PDF. docx ו-png — בליבה (`custom.xml`, `customXml/item1.xml` + `itemProps`, ‏`[Content_Types].xml` ו-rels; ‏`iTXt` אחרי IHDR) |
| ב | מזהה פסקה | שם סימנייה ב-Word: עד 40 תווים, `[A-Za-z0-9_]` **בלי מקף**. לכן המזהה מצטמצם ל-**`[A-Za-z0-9_]{1,32}`** (‏`_mbe_p` + 32 = 38). מזהה חדש מהליבה: `p` + 10 תווים אלפאנומריים. **שינוי באפיון — בקשה:** [`requests/spec-para-id.md`](../requests/spec-para-id.md) |
| ג | `reconcile` | **לא משנה את `f`** — מחזיר תוכנית. ‏`applyMerge` משנה את `f.document`, ושלבי `return` ו-`merge` נכתבים בשמירה הבאה |
| ד | יומן | שמירות רצופות מעדכנות את `result` של השלב האחרון, **והעותק הקודם נמחק מ-`history/`** אם אף שלב לא מפנה אליו. ‏`who` — `save(f, { who })`. ‏`f.stage()` — נכתב בשמירה הבאה |
| ה | קודים | כל השמות בסעיף 5, ועוד `face-not-saved` (‏`stampFace` על מסמך שהשתנה מאז השמירה). `history-*` ו-`para-id-*` — **אזהרות**: היסטוריה פגומה לא חוסמת פתיחה |
| — | `stampFace` ו-`save` | **אחרי `save`** — `f` כבר נושא את `manifest.document.sha256` החדש, ו-`stampFace` קורא אותו |
| — | נפילה לפי תוכן | לא LCS נאיבי (5000×5000 = 25 מיליון תאים): עוגנים לפי טקסט זהה וייחודי (patience diff), LCS רק ביניהם, "פסקה שנערכה" — Dice על מילים מעל 0.6. מעל 5000 פסקאות בקטע בלי עוגן — רק עוגנים, ו-`gaps` אומר |

## 7. בדיקות שהליבה צריכה (כולן בלי Word אמיתי)

- הלוך-חזור: `stampFace` → `identify` מחזיר אותו `docId` ו-`base`, ב-JS וב-PHP זהה.
- שלושת המקרים של `reconcile` (`fast-forward`, `diverged` עם התנגשות, `other-doc`), כולל פסקה חדשה בלי `id` ופסקה שנמחקה.
- docx שחזר בלי זיכרון: בסיס מ-`customXml`; שכבה שאינה בטקסט → `gaps`.
- יומן: שמירות רצופות באותה אפליקציה = שלב אחד; `restore` לא מוחק.

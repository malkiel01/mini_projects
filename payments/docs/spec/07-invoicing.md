## 7.4 שתי ארכיטקטורות

| | **א. ספק חשבוניות נפרד** (Morning / iCount) | **ב. מסמכים של הסולק** (Cardcom / PayPlus Invoice+ / Morning-סליקה) |
| --- | --- | --- |
| זרימה | תשלום מאושר → התוסף קורא ל-API של הספק → מסמך | הסולק מפיק מסמך עם העסקה (דגל `initial_invoice` וכד') |
| יתרון | **ספר מסמכים אחד** לכל הסולקים; החלפת סולק לא נוגעת בחשבוניות; רו"ח רואה הכול במקום אחד | אפס אינטגרציה נוספת; אטומי עם התשלום |
| חיסרון | עוד מנוי; קריאה נוספת שיכולה להיכשל (→ תור `tax_docs`) | ספר מסמכים לכל סולק; מסמכים ידניים/מזומן — במקום אחר |

**ההמלצה: א' עם Morning** — ובמקרה שבו הסולק **הוא** Morning (סליקה מובנית), שני הדברים מתאחדים: התשלום מפיק
את המסמך, ואנחנו רק שומרים את המספר והקישור. מחבר `InvoiceProvider` בממשק משלו:

```php
interface InvoiceProvider {
  public function issue(Invoice $inv, Payment $p, Account $a): TaxDoc;     // 320 / 400 / 305
  public function credit(Refund $r, TaxDoc $orig): TaxDoc;                  // 330
  public function manual(Payment $p, Account $a): TaxDoc;                   // מזומן/צ'ק/העברה
  public function get(string $id): TaxDoc;                                  // מספר, הקצאה, PDF
}
```

מחברים: `morning`, `icount`, `provider` (המסמך מגיע מהסולק), `none` (בדיקות — מסמך "טיוטה" פנימי, **לא חשבונאי**).

## 7.5 פרטים שהמסמך צריך מאיתנו

שם הלקוח (או שם העסק), ח"פ/ע"מ/ת"ז (B2B, ולבקשת מספר הקצאה), מייל, כתובת (אופציונלי), שורות (תיאור, כמות,
מחיר), הנחה, מע"מ, אמצעי תשלום (סוג, 4 ספרות, מספר תשלומים, אסמכתא), תאריך, מטבע, הערה: "ביטול המנוי — בקישור
X / במייל Y / בטלפון Z".

# פרק 9 — תפעול: מחזור החיוב, גבייה, התאמה ותקלות

## 9.1 התזמון

cPanel מאפשר cron. משימה אחת כל 5 דקות: `php payments/cron.php` — מריצה את תור העבודות (`job`) עם נעילה
(`locked_until`), כך שהרצה כפולה לא מחייבת פעמיים. ❓ אם אין cron — "cron של עני": כל בקשה ל-API מריצה עד
עבודה אחת שהגיע זמנה (פחות אמין; רק גיבוי).

| עבודה | תדירות |
| --- | --- |
| `webhook_deliver` — שליחה וניסיונות חוזרים לאפליקציות | כל 5 דקות |
| `renew` — מנויים שהמחזור נגמר → חשבונית → חיוב | כל שעה |
| `dunning` — ניסיונות חוזרים לחשבוניות פתוחות | כל שעה |
| `auto_topup` — ארנקים מתחת לסף | כל 5 דקות (וגם מיד אחרי `usage_record`) |
| `reservations_expire` | כל 5 דקות |
| `tax_docs` — מסמכים שלא הופקו (ספק החשבוניות נפל) | כל 15 דקות |
| `reminders` — חידוש קרוב, ניסיון נגמר, כרטיס פג | יומי 09:00 |
| `reconcile` — התאמה מול הסולקים | יומי 03:00 |
| `integrity` — בדיקת שלמות (פרק 3.4) | יומי 03:30 |
| `backup` | יומי 04:00 |
| `cleanup` — nonce, idempotency, סשנים | יומי |

## 9.2 חידוש מנוי — צעד אחר צעד

1. נועלים את המנוי (`job` אחד לכל מנוי).
2. בונים חשבונית: שורות המנוי למחזור הבא (מראש) + שימוש מדוד של המחזור שנגמר (בדיעבד) + יחידות שנצברו +
   הנחות. מחשבים מע"מ.
3. סכום 0 → חשבונית `paid` בלי חיוב (ניסיון, קופון 100%).
4. ארנק עם יתרה → מקזזים קודם מהארנק (❓ לפי הגדרה).
5. מחייבים מהאמצעי ברירת המחדל (טוקן, off-session) **עם מפתח idempotency של הסולק** = `inv_…:attempt`.
6. הצלחה → `payment succeeded`, `invoice paid`, מסמך חשבונאי, תקופה חדשה, webhooks.
7. כשל → `past_due`, לוח ניסיונות (9.3), webhook, מייל.

## 9.3 גבייה של כשלים (dunning)

| יום | פעולה |
| --- | --- |
| 0 | כשל → מייל "עדכון אמצעי תשלום" + `subscription.past_due` |
| 1 | ניסיון חוזר |
| 3 | ניסיון חוזר + מייל |
| 7 | ניסיון אחרון + מייל "השירות ייעצר" — **סוף ימי החסד** (ברירת מחדל) |
| 14 | `canceled` (או `paused` — ❓ לפי מוצר) + `invoice uncollectible` |

- קודי סירוב "קשים" (כרטיס גנוב/חסום/לא קיים) — לא מנסים שוב; רק מבקשים אמצעי אחר.
- עדכון אמצעי תשלום בפורטל → ניסיון מיידי של כל החשבוניות הפתוחות.

## 9.4 webhook נכנס מסולק — הטיפול

```
1. שמירה גולמית ב-provider_event (ייחודי לפי מזהה האירוע) — כפילות → 200 ומסיימים
2. אימות לפי הסולק (חתימה / סוד / IP — פרק 5)
3. שאילתה חוזרת לסולק: "מה מצב העסקה X?" — סומכים רק על התשובה הזו
4. השוואה: סכום, מטבע, checkout/חשבונית שלנו
5. טרנזקציה: payment, invoice, subscription, wallet, token
6. תור: מסמך חשבונאי, webhooks לאפליקציה, מייל
7. 200 לסולק (תמיד מהר — העבודה הכבדה בתור)
```

גם אם ה-webhook לא מגיע (תקלה אצל הסולק), `pay/return.php` והתאמה כל שעה ל-checkouts פתוחים מגלים את
העסקה דרך השאילתה.

## 9.5 התאמה (reconciliation)

כל לילה, לכל חיבור סולק: מושכים את העסקאות של אתמול (API או דוח) ומשווים ל-`payment`:

| פער | פעולה |
| --- | --- |
| עסקה אצל הסולק, לא אצלנו | יוצרים `payment` (אם יש checkout מתאים) או מתריעים |
| אצלנו `succeeded`, אצל הסולק לא | התראה דחופה — לא מעניקים שוב |
| סכום שונה | התראה |
| החזר אצל הסולק שלא נרשם | רושמים + מסמך זיכוי |
| מסמך חשבונאי חסר לתשלום | `tax_docs` |

וגם: **הפקדות** (settlement) מהסולק לבנק מול סכום העסקאות פחות עמלות — דוח חודשי למנהל ❓ (תלוי ב-API של
הסולק).

## 9.6 החזרים

- מהמנהל בלבד (או API `refund` לאפליקציה — ❓ ברירת מחדל: לא).
- מלא או חלקי; דרך אותו סולק ואותו אמצעי (ביט → החזר לביט, אם הסולק תומך — פרק 6).
- מסמך זיכוי (חשבונית מס זיכוי / קבלה שלילית) — אוטומטי דרך ספק החשבוניות.
- החזר על טעינת ארנק — רק עד היתרה שלא נוצלה.
- **chargeback** (הכחשת עסקה) — מהסולק כאירוע; מנוי מושהה, התראה למנהל, תיעוד ראיות.

## 9.7 גיבוי ושחזור

- גיבוי יומי של המסד (`VACUUM INTO`), מוצפן ב-`secret.key`, 30 יום ב-`data/backups/`.
- ❓ עותק מחוץ לשרת (מייל מוצפן / Drive / ריפו פרטי נפרד) — כסף וחשבוניות לא יכולים להיות רק בשרת אחד.
- **`secret.key` חייב גיבוי נפרד** אצל בעל המערכת (בלעדיו הטוקנים והסודות לא ניתנים לפענוח). הוראות במסך
  ההגדרות.
- מקור האמת החשבונאי הוא ספק החשבוניות והסולק — אפשר לבנות מחדש תשלומים מהם במקרה קיצון.

## 9.8 ניטור ויומן

- יומן מובנה `data/logs/` + DevLoop (שגיאות → ⚠️ לבירור) ❓ — לחבר את התוסף ל-DevLoop כמו שאר האפליקציות.
- התראות למנהל (מייל/push): webhook של סולק נכשל באימות, פער התאמה, ספק חשבוניות לא זמין שעה, 5 כשלי
  חיוב ברצף בסולק (אולי הסולק נפל), אפליקציה ממתינה לאישור.
- `health.php` — מצב: מסד, cron אחרון, סולקים (ping), ספק חשבוניות.

## 9.9 פריסה

- `php platform/check-apps.php` לפני push.

# תוסף התשלומים — אפיון (טיוטה, שלב 1)

> מצב: **טיוטה לפני הכרעות.** כל מה שמסומן ❓ מחכה להכרעה של בעל המערכת (פרק 11).
> אין עדיין קוד. העמלות והמגבלות של חברות הסליקה — **מהזיכרון ומאתרים מסחריים, לאמת מול הצעת מחיר**.

## 1. מה זה

תוסף בפלטפורמה (`payments/`, `"plugin": true`, `"gate": true`) שמנהל את כל הגבייה מלקוחות של האפליקציות:
מנוי, תשלום לפי יחידה (דוח, פרויקט) ושימוש מדוד (טוקנים של AI). הוא מחזיק את חשבון החיוב של הלקוח,
מפיק חשבוניות כחוק, ומדבר עם חברת הסליקה.

**מה הוא לא:**

- לא מחזיק פרטי כרטיס. אף פעם. רק טוקן של הסולק.
- לא מערכת משתמשים. הלקוח המשלם הוא לקוח של **אפליקציה**; התוסף מכיר אותו רק דרכה.
- לא נטען ב-`require` מאפליקציה. אפליקציה מדברת איתו כמו עם Stripe — HTTP חתום.

```
 אפליקציה (שרת)  ──API חתום──▶  תוסף התשלומים  ──API──▶  סולק (דף מתארח, טוקן, חיוב)
       ▲                           │   ▲                         │
       └────── webhook חתום ───────┘   └──── webhook של הסולק ───┘
                                   │
                                   └──API──▶  ספק חשבוניות (Morning / iCount / של הסולק)
 דפדפן הלקוח ──▶ דף תשלום מתארח בתוסף ──▶ דף/iframe של הסולק
```

## 2. מודלי חיוב

| מודל | דוגמה | איך נגבה |
| --- | --- | --- |
| **מנוי** | 49 ₪ לחודש למנהל הפרויקטים | חיוב חוזר מטוקן, בכל מחזור (חודש/שנה). ניסיון חינם אופציונלי |
| **לפי יחידה** | 15 ₪ לכל דוח, 200 ₪ לכל פרויקט | חיוב מיידי (קנייה) **או** צבירה לחשבון וגבייה בסוף המחזור |
| **שימוש מדוד** | 0.02 ₪ לכל 1,000 טוקנים | ❓ **מראש** — ארנק קרדיט שיורד עם כל אירוע, טעינה ידנית או אוטומטית מתחת לסף; **או בדיעבד** — צבירה וחיוב בסוף המחזור, עם תקרה |
| **שילוב** | מנוי שכולל 1M טוקנים, ומעבר לכך לפי שימוש | מנוי + מכסה (`included`) + חריגה (`overage`) |

**כללי התמחור (לכל מחיר):** סכום באגורות (שלם, בלי שברים), מטבע, מע"מ כלול/לא, מחזור, מדרגות
(`tiers`: עד X ביחידה Y), מכסה כלולה, תקרה חודשית. מחיר לא נערך אחרי שמישהו נרשם עליו — יוצרים גרסה
חדשה, והמנויים הקיימים נשארים על הישנה עד שמעבירים אותם.

**יחסי (proration):** שדרוג/שנמוך באמצע מחזור — זיכוי על היתרה וחיוב יחסי על התכנית החדשה, בחשבונית אחת.
ביטול — עד סוף המחזור ששולם (ברירת מחדל), או מיידי עם זיכוי.

**"חשבון יחסי לפי האפליקציות":** חשבון חיוב אחד יכול להחזיק מנויים בכמה אפליקציות; החשבונית החודשית
מפרטת שורה לכל אפליקציה, ובמסך המנהל רואים הכנסה לכל אפליקציה.

## 3. הישויות

```
app ──< price_plan(product) ──< price
 │
 └──< customer (app, external_id) >──── account ──< payment_method (token)
                                           │
                     ┌─────────────────────┼──────────────────┬──────────────┐
                subscription          usage_event        wallet_tx       invoice ──< invoice_line
                                                                            │
                                                                         payment ──< refund
```

| ישות | שדות עיקריים | הערות |
| --- | --- | --- |
| `app` | `id` (שם התיקייה), שם, `key_url`, מפתחות, `webhook_url`, סטטוס | רישום עצמי כמו ב-`embed.md` §1 |
| `product` | `app`, `code` (`report`, `project`, `ai_tokens`, `pro_plan`), שם, סוג (`subscription`/`unit`/`metered`) | |
| `price` | `product`, גרסה, סכום, מטבע, מחזור, `tiers`, `included`, מע"מ כלול, פעיל | לא נערך — רק גרסה חדשה |
| `customer` | `app`, `external_id` (המזהה של הלקוח באפליקציה), שם, מייל, `account` | ייחודי ל-(`app`, `external_id`) |
| `account` | שם לחשבונית, ח"פ/ע"מ/ת"ז, כתובת, מייל לחשבוניות, יתרת קרדיט, אמצעי ברירת מחדל | ❓ חשבון אחד לכמה לקוחות — רק בקישור מפורש |
| `payment_method` | `account`, טוקן הסולק, 4 ספרות, תוקף, מותג | **בלי מספר כרטיס ובלי CVV** |
| `subscription` | `account`, `customer`, `price`, סטטוס (`trialing`/`active`/`past_due`/`canceled`), תחילת/סוף מחזור, `cancel_at` | |
| `usage_event` | `customer`, `product`, כמות, `idempotency_key`, זמן, `meta` | ייחודי ל-(`app`, `idempotency_key`) |
| `wallet_tx` | `account`, סכום (+/-), סיבה, הפניה | יתרה = סכום התנועות. לא עמודה שמתעדכנת |
| `invoice` | `account`, מספר, שורות, סה"כ, מע"מ, סטטוס (`draft`/`open`/`paid`/`void`), מסמך חשבונאי חיצוני + קישור | |
| `payment` | `invoice`, סכום, סטטוס, מזהה עסקה בסולק, אישור, מספר תשלומים | |
| `refund` | `payment`, סכום, סיבה, מסמך זיכוי | |
| `webhook_out` | יעד, אירוע, גוף, ניסיונות, סטטוס | תור שליחה חוזרת |
| `audit` | מי (מנהל/אפליקציה/סולק/מערכת), מה, לפני/אחרי, זמן, IP | רק הוספה |

**המסד:** SQLite ב-`payments/data/payments.sqlite` (כמו שאר הכלים), WAL, גיבוי יומי לקובץ בתיקייה מוחרגת.
החרגה ב-`deploy.yml`: `--exclude='payments/data/'`.

## 4. החיבור בין אפליקציה לתוסף

### 4.1 רישום

כמו `platform/docs/embed.md` §1, עם אותה הגנה: האפליקציה יוצרת זוג Ed25519 **במסד שלה**, מפרסמת את
המפתח הציבורי בכתובת שלה, ונרשמת:

```
POST payments/api.php?action=app_register
{"app":"project-manager","name":"מנהל הפרויקטים",
 "key_url":"https://mbe-plus.com/mini_projects/project-manager/api.php?action=embed_key",
 "webhook_url":"https://mbe-plus.com/mini_projects/project-manager/api.php?action=payments_webhook",
 "origins":["https://mbe-plus.com"]}
→ {"status":"pending"}      // תמיד pending — המנהל מאשר בלשונית "אפליקציות"
```

שונה מהעורך: **כל רישום ממתין לאישור המנהל**, גם מאותו דומיין — כי מדובר בכסף.

### 4.2 חתימה

בדיוק `embed.md` §2: `X-Embed-Client/Time/Nonce/Signature`, Ed25519 על
`<action>\n<time>\n<nonce>\n<sha256(body)>`, ±300 שניות, nonce נשמר 10 דקות. הקוד מועתק לתוסף (לא
`require` ל-`platform/lib/provision.php`).

### 4.3 ה-API (שרת-לשרת, חתום)

`POST payments/api.php?action=<פעולה>`. שגיאה: `{"error":"<עברית>","code":"..."}`.
כל פעולה שיוצרת משהו מקבלת `Idempotency-Key` (כותרת); אותה מפתח + אותו גוף → אותה תשובה (24 שעות);
אותו מפתח + גוף אחר → 409 `idempotency_mismatch`.

| פעולה | גוף | תשובה |
| --- | --- | --- |
| `customer_upsert` | `{external_id, name, email, tax_id?}` | `{customer, account}` |
| `checkout_create` | `{external_id, items:[{product, price?, qty}] \| subscribe:{price} \| topup:{amount}, return_url, cancel_url}` | `{checkout_id, url, expires_in}` |
| `subscription_get` | `{external_id}` | `{subscriptions:[…]}` |
| `subscription_change` | `{subscription, price, prorate:true}` | `{subscription, invoice?}` |
| `subscription_cancel` | `{subscription, at:"period_end"\|"now"}` | `{subscription}` |
| `usage_record` | `{external_id, product, quantity, idempotency_key, at?}` | `{event, balance?, allowed}` |
| `usage_batch` | `{events:[…]}` (עד 500) | `{accepted, duplicates, rejected:[…]}` |
| `entitlement` | `{external_id, product?}` | `{active, plan, balance, limits, until}` |
| `charge_unit` | `{external_id, product, qty, description}` | `{payment\|invoice, status}` — חיוב מיידי מטוקן שמור |
| `portal_session` | `{external_id, return_url}` | `{url}` — דף "החשבון שלי" ללקוח |
| `invoices_list` | `{external_id, after?}` | `{invoices:[…], next?}` |

**`entitlement` הוא הלב:** לפניו האפליקציה מחליטה אם לאפשר פעולה (ליצור דוח, לשלוח לבינה מלאכותית).
האפליקציה שומרת עותק במטמון (דקה–חמש) ומתעדכנת מ-webhook, כדי שתקלה בתוסף לא תעצור את האפליקציה —
❓ ברירת מחדל כשהתוסף לא עונה: **לאפשר** (עדיף לא לחסום לקוח משלם) עם רישום ביומן.

**טוקנים בתשלום מראש:** `usage_record` מוריד מהארנק אטומית ומחזיר `allowed:false` כשאין יתרה. כדי לא
לעשות קריאה לכל הודעה — האפליקציה יכולה **לשריין** (`usage_reserve {estimate}` → `reservation`), ואחר כך
לסגור בכמות בפועל (`usage_commit {reservation, quantity}`). שריון שלא נסגר פג תוך 15 דקות.

### 4.4 דפים מתארחים (ציבוריים)

| כתובת | מה |
| --- | --- |
| `pay/?c=<checkout_id>` | דף התשלום: סיכום, פרטי חשבונית, ואז iframe/הפניה לדף של הסולק. בלי התחברות — ה-`checkout_id` חד-פעמי, אקראי, פג תוך שעה |
| `portal/?s=<token>` | "החשבון שלי": מנוי, אמצעי תשלום (החלפה דרך הסולק), חשבוניות להורדה, ביטול |
| `hooks/<provider>.php` | webhook מהסולק — מאומת לפי מנגנון הסולק **וגם** בשאילתה חוזרת לסולק לפני שמסמנים "שולם" |

כולם ב-`"public"` של `payments/app.json`; כל השאר מאחורי השער (רק המנהל).

### 4.5 webhooks לאפליקציה

`POST <webhook_url>` חתום **על ידי התוסף** באותו פרוטוקול (התוסף מפרסם `?action=key`), כדי שהאפליקציה
תאמת. אירועים:

`checkout.completed` · `payment.succeeded` · `payment.failed` · `subscription.created|updated|canceled|past_due`
· `invoice.issued` · `wallet.low` · `wallet.empty` · `refund.created`

גוף: `{id, type, created, data:{…}}`. האפליקציה מחזירה 2xx; אחרת ניסיון חוזר אחרי 1, 5, 30 דקות, 2, 6, 24 שעות.
`id` ייחודי — האפליקציה מתעלמת מכפילות. **ה-webhook הוא רמז**: לפני החלטה חשובה — `entitlement`.

### 4.6 ספריית לקוח (SDK)

`payments/sdk/payments-client.php` — קובץ אחד, בלי תלויות, שכל אפליקציה **מעתיקה** אליה (כמו DevLoop):
יצירת מפתחות ופרסומם, רישום, חתימה, קריאות ה-API, אימות webhook, מטמון זכאות. + `payments/docs/connect.md`
— המדריך לצ'אט של אפליקציה. ❓ האם להעתיק ב-`sync.php` כמו DevLoop (וכך שער בפריסה) — מחייב בקשה לצ'אט
הפלטפורמה; בינתיים העתקה ידנית עם מספר גרסה בראש הקובץ.

## 5. מחזור החיוב (cron)

פעם בשעה (cron בשרת, ❓ או "cron של עני" מתוך בקשות):

1. מנויים שהמחזור שלהם נגמר → חשבונית (מנוי + שימוש מדוד בדיעבד + יחידות שנצברו) → חיוב מטוקן.
2. כשל → `past_due`, ניסיונות חוזרים (יום 1, 3, 7), מייל ללקוח עם קישור להחלפת כרטיס; אחרי 14 יום →
   `canceled` (❓ או השעיה). webhook לאפליקציה בכל שינוי.
3. ארנקים עם טעינה אוטומטית מתחת לסף → טעינה.
4. תור ה-webhooks — שליחה חוזרת.
5. התאמה (reconciliation) יומית: עסקאות בסולק מול `payment`; פער → התראה למנהל.

## 7. סליקה בישראל — השוואה

> לאמת מחירים בהצעה בכתב. רוב הסולקים בישראל דורשים גם **הסכם סליקה עם חברת אשראי** (ישראכרט/כאל/מקס)
> ועמלה לחברת האשראי בנפרד מדמי הסולק; Grow ו-PayPlus מציעים גם מסלול "הכול כלול".

| סביבת בדיקות | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

**ההמלצה (לפני הכרעה):** **PayPlus** או **Cardcom**. שניהם: דף מתארח (אצלנו אפס PCI מעבר ל-SAQ-A), טוקן
לחיוב חוזר שאנחנו מפעילים (כך מודל השימוש והחיוב היחסי נשארים אצלנו ולא תלויים במנויים של הסולק), webhook,
ביט, וחשבוניות מובנות כאופציה. PayPlus — API מודרני יותר; Cardcom — הוותיק והנפוץ, הרבה דוגמאות.
**הקוד ייכתב מאחורי ממשק `Provider`** (יצירת דף, אימות webhook, חיוב מטוקן, החזר, שאילתה) — כך שהחלפת סולק
היא קובץ אחד.

## 8. חשבוניות כחוק

- **עוסק פטור:** מפיק **קבלה** בלבד, בלי מע"מ. ❓
- **עוסק מורשה / חברה:** **חשבונית מס/קבלה** בכל תשלום, מע"מ 18% (מינואר 2025). חשבונית מס לעוסק מורשה מעל
  הסף — **מספר הקצאה** מרשות המסים ("חשבוניות ישראל"; לפי פרסומים, הסף ירד ל-5,000 ₪ לפני מע"מ ביוני 2026 —
  לאמת). ספק חשבוניות מוכר מטפל בזה לבד.
- **אנחנו לא מפיקים מסמך חשבונאי בעצמנו** (מספור רציף, תוכנה רשומה ברשות המסים) — רק דרך ספק.

| ספק | יתרונות | חסרונות |
| --- | --- | --- |
| **Morning (חשבונית ירוקה)** | API טוב (מסמכים 320/400/305), מספר הקצאה אוטומטי, מחובר לסולקים רבים, נפוץ אצל רואי חשבון | עוד מנוי חודשי |
| **iCount** | API מלא, גם הנהלת חשבונות | ממשק פחות נוח |
| **של הסולק** (Cardcom / PayPlus Invoice+) | אפס אינטגרציה נוספת — המסמך נוצר עם העסקה | קשור לסולק; החלפת סולק = החלפת ספרי חשבוניות |

**ההמלצה:** **Morning**, גם הוא מאחורי ממשק `InvoiceProvider`. התוסף שומר את מספר המסמך ואת הקישור ל-PDF,
והלקוח מוריד מ"החשבון שלי".

## 9. אבטחה

- **PCI:** אין לנו מספרי כרטיס — רק דף מתארח/iframe של הסולק וטוקן. אין שדות כרטיס בדף שלנו.
- **אפליקציות:** Ed25519 (4.2), רישום רק באישור מנהל, אפליקציה רואה רק את הלקוחות שלה (לקוח של אחרת → 404).
- **סולק → אנחנו:** אימות לפי הסולק (חתימה/סוד) **+ שאילתת אימות** לסולק על העסקה לפני שינוי מצב. סכום
  ומטבע מושווים ל-`checkout` שלנו.
- **אנחנו → אפליקציה:** webhooks חתומים, `id` ייחודי.
- **Idempotency:** בכל יצירה (4.3), וב-`usage_event` לפי `idempotency_key` — שימוש לא נספר פעמיים.
- **כסף:** אגורות בשלמים; יתרה מחושבת מתנועות; כל שינוי ביתרה בטרנזקציה של המסד (`BEGIN IMMEDIATE`).
- **סודות** (מפתחות API של הסולק וספק החשבוניות): ב-`payments/data/config.json` (מוחרג), הרשאות 600, לא
  בגיט, לא נשלחים לדפדפן. מצב בדיקה/חי במתג.
- **ביקורת:** טבלת `audit` רק-הוספה; כל פעולת מנהל (החזר, זיכוי, שינוי מחיר) נרשמת עם לפני/אחרי.
- **פרטיות:** מינימום פרטים על הלקוח (שם, מייל, מספר עוסק לחשבונית). מחיקת לקוח = אנונימיזציה (החשבוניות
  נשמרות 7 שנים לפי חוק).

## 10. שלבי מימוש

1. **שלד:** `app.json` (plugin + gate + public), `index.html` RTL, README, אייקון, מסד ריק, החרגה בפריסה.
2. **ליבה בלי כסף אמיתי:** אפליקציות + חתימה, לקוחות, מוצרים ומחירים, `entitlement`, `usage_record`, ארנק
   עם טעינה ידנית של המנהל. ספק "דמה" (`fake`) מאחורי `Provider`.
3. **סולק בסביבת בדיקות:** דף תשלום, טוקן, webhook, חיוב מנוי, cron.
4. **חשבוניות** דרך הספק שנבחר.
5. **SDK + מדריך**, וחיבור האפליקציה הראשונה (על ידי הצ'אט שלה).

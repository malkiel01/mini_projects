## הרצת הבדיקות

```bash
python3 recipes-app/tools/schema-check.py    # הסכימה וההבטחות שלה
php     recipes-app/tools/auth-check.php     # שכבת החשבונות
php     recipes-app/tools/recipes-check.php  # שכבת המתכונים
php     recipes-app/tools/social-check.php   # תגובות, פתקים, מועדפים
php     recipes-app/tools/log-check.php      # יומן וטוקן צפייה
php     recipes-app/tools/import-check.php   # ייבוא מהרשת (קבצי דוגמה)
php     recipes-app/tools/ai-check.php       # ניסוח בבינה וסודות
php     recipes-app/tools/scout-check.php    # סורק אתרים
php     recipes-app/tools/pantry-check.php   # מה יש לי בבית
php     recipes-app/tools/shopping-check.php # רשימת קניות ומצב בישול
bash    recipes-app/tools/api-check.sh       # ה-API מקצה לקצה, על שרת אמיתי
bash    recipes-app/tools/shot.sh out.png '#/r/1'   # צילום ברוחב טלפון, מחובר ועם מתכון בדיקה
```

שתיהן רצות על מסד בזיכרון או בתיקייה זמנית, ואינן נוגעות בנתונים האמיתיים.

## נתונים בשרת

`data/recipes.sqlite` ו-`data/media/` נוצרים בשרת ואינם בגיט. **שתי שורות
ה-`--exclude` כבר נמצאות ב-`deploy.yml`**, והן נכנסו באותה דחיפה שבה נכתב
`db.php` — לא אחריה. בלעדיהן פריסה מוחקת מתכונים ומדיה, ואין שחזור.

ל-`data/` ול-`data/media/` יש `.htaccess` משלהן, והן שונות בכוונה: הראשונה
חוסמת הכול, והשנייה מגישה תמונות וסרטונים אבל מונעת הרצת קוד — כי לשם
מעלים קבצים אנשים שאינני מכיר.

ל-`recipes-app/` עצמה יש `.htaccess` שלישי, שכל תפקידו `Cache-Control:
no-cache` ל-HTML/JS/CSS. בלעדיו הטלפון מחזיק גרסה ישנה של הדף ימים
שלמים, ותכונה שנפרסה פשוט לא מופיעה — בלי שום שגיאה. בנוסף לזה, לתגי
ה-`<script>` וה-`<link>` ב-`index.html` יש `?v=` שמתחלף כשהקבצים משתנים.

## מצב נוכחי

עובד: חשבונות (הרשמה, אימות, כניסה, איפוס), מתכון מקצה לקצה (יצירה, תצוגה עם המרת מנות,
עריכה, מחיקה), חיפוש בשם וברכיבים, מדיה, הגדרות וניהול משתמשים, תגובות בשתי רמות,
פתק פרטי על כל מתכון, מועדפים ששורדים מחיקה של המקור, אבחון למנהל, ויומן.

## ייבוא מהרשת

☰ → ייבוא מהרשת: מדביקים קישור לדף מתכון, והשרת מביא אותו (`lib/importer.php`)
ומחלץ שם, רכיבים, שלבים, זמנים, כמות, תמונות וסרטון — בשלוש שכבות: JSON-LD של
schema.org/Recipe (רוב האתרים, כולל הישראליים), Microdata, וניחוש לפי כותרות
("מצרכים", "אופן ההכנה"). התוצאה נפתחת **בעורך** כטיוטה; שום דבר לא נשמר עד
"צור מתכון". הרכיבים עוברים פענוח לשכבה המחושבת ("2 כוסות (400 גרם) קמח" →
2, כוס, קמח), הטקסט החופשי נשאר כמו במקור.

**קרדיט:** `source_url` / `source_name` / `source_author` נשמרים במתכון, מוצגים
תמיד בתצוגה (עם קישור) וברשימה (🌐 שם האתר), ואינם ניתנים לשינוי בעריכה.
התמונות והסרטונים נשמרים **כקישורים** לכתובת המקורית — לא מועתקים לשרת ולא
נספרים במקצב. מתכון מיובא נוצר פרטי; הפרסום לציבור הוא החלטה של המשתמש, והעורך
אומר לו זאת. ברשימה יש מסנן "מהרשת".

**אבטחה:** השרת מביא כתובת שמשתמש זר הקליד, ולכן: רק http/https, רק פורטים
80/443, לא כתובות פנימיות (גם אחרי הפניה), עד 3MB, עד 15 שניות. בבדיקות בלבד
`IMPORT_ALLOW_LOCAL` פותח את השרת המקומי, ושרת שני מגיש את קבצי הדוגמה — כי
השרת המובנה של PHP חד-חוטי.

## תיעוד פרטי וניסוח מחדש

**תיעוד פרטי** (`import_snapshots`): עם שמירת מתכון מיובא נשמר מה בדיוק חולץ מהמקור —
שם, רכיבים, שלבים כלשונם, זמנים, תמונות, כותב — כ-JSON של כמה קילובייט. רואה אותו רק
המייבא (במתכון: "המקור כפי שיובא"), לא מוצג לציבור לעולם, ונמחק עם המתכון. זה מה שנשאר
כשהאתר המקורי מוריד את הדף.

**ניסוח מחדש בבינה** (`lib/ai.php`): כפתור "✨ נסח מחדש בבינה" בעורך של מתכון מיובא.
השלבים נשלחים ל-Claude API (מודל `claude-opus-5-5`, פלט מובנה לפי סכימה, בקשת HTTP
ישירה ב-cURL — בלי SDK, כי אין כאן Composer ולא שלב בנייה) עם הוראה לשמור כל כמות,
טמפרטורה, זמן וסדר, ולשנות מילים ומבנה. אחרי התשובה נמדד דמיון למקור (שיעור השלבים
שזהים למשפט מקורי); מעל 30% — ניסיון שני, ואם עדיין — אזהרה והמשתמש מחליט. יש "בטל
ניסוח". מתכון שנוסח מחדש מקבל `source_rewritten=1`, והקרדיט הופך ל"מבוסס על המתכון
של…". זכות יוצרים מגנה על הניסוח ולא על השיטה — ולכן זה מה שמוריד את החשיפה.

**המפתח** נשמר ב-`data/secrets.json` (0600, מחוץ לגיט ולפריסה) דרך הגדרות ציבוריות →
מפתחות API. ה-API לא מחזיר אותו אף פעם, רק סיומת לזיהוי; `secret-set` מוציא את הערך
מהיומן. עלות: מתכון הוא כמה מאות טוקנים לכל כיוון — שבריר אגורה.

## מה יש לי בבית

☰ → מה יש לי בבית (`lib/pantry.php`, לכל משתמש מחובר). מזינים מוצרים בהקלדה
(פסיקים מפרידים) או **בצילום**: התמונה מכווצת בדפדפן, נשלחת ל-`pantry.php`, Claude
מזהה את המוצרים (פלט מובנה, בלי לשמור את התמונה), והמשתמש מסמן מה להוסיף. דורש
מפתח API; בלעדיו — הקלדה. "מוצרי יסוד" (מלח, שמן, מים…) נחשבים קיימים, וכל אחד
ניתן לכיבוי.

ההתאמה (`pantryMatch`) עוברת על כל המתכונים שהמשתמש רואה ומדרגת לפי כיסוי: כמה
מהרכיבים שאינם רשות יש לו. ההשוואה טקסטואלית — נרמול, גזע עברי גס (עגבניות ↔
עגבנייה, ביצים ↔ ביצה), והכלה: "שמן" מכסה "שמן קנולה" אבל "שמן זית" לא. המסך
מציג "חסר: …" ומסנן לפי כמה מותר שיחסר (0–3).

## סורק אתרים — כלי פרטי של המפתח

☰ → סורק אתרים (`lib/scout.php`, למפתח בלבד). מדביקים דף קטגוריה, דף בית או
sitemap של אתר מתכונים; הסורק מציע מועמדים (קישורים שנראים כמו דפי מתכון, או כל
ה-`<loc>` של sitemap), האדם מסמן ✓/✕, והמסומנים מיובאים אחד-אחד: הבאה → מתכון
פרטי עם קרדיט ותיעוד → תמונות כקישורים → ניסוח מחדש בבינה (אם ביקשו ויש מפתח).

חצי ידני, חצי אוטומטי — בכוונה, כדי לא להיראות כמו בוט ולא להעתיק המונית:
- robots.txt של האתר נבדק (מטמון ליום), ודף אסור לא מובא.
- מרווח מינימלי בין הבאות מאותו דומיין בצד השרת (3 שניות), והדפדפן מוסיף
  מרווח של 3–60 שניות (ברירת מחדל 8) עם אקראיות בין פריטים.
- User-Agent מזהה את האפליקציה. אין סריקה רקורסיבית: דף רשימה אחד = בקשה אחת.
- הכול נרשם ביומן (`scout-page`, `scout-import`), וכל הבאה — ביומן הייבוא.
- קישורים שנראים כמו תבנית JavaScript שלא רונדרה (`/foody_recipe/' + product_url + '`),
  קישורי שיתוף מקוננים (`…/whatsapp://send?…`) ודף הרשימה עצמו — אינם מועמדים.

## יומן ייבוא

כל הבאה של דף מהרשת — ייבוא מהעורך, תצוגה מקדימה וייבוא בסורק, משיכה חוזרת של
תיעוד — נרשמת ב-`import_log` (`lib/import_log.php`), גם כשנכשלה. לכל שורה:
קישור למקור, מה היה בדף (כמה JSON-LD ואילו `@type`, באיזו צורה `recipeInstructions`
ותחילתו כלשונו, Microdata, הכותרות h1–h4, כמה רשימות, og:title), ומה חולץ ממנו
כלשונו (הרכיבים עם הפענוח לשכבה המחושבת, השלבים, מנות, זמנים, תמונות, קרדיט),
עם האזהרות. שמירה מהעורך של טיוטה שיובאה נרשמת גם היא (`editor-save`): כמה
רכיבים ושלבים נשמרו בסוף, מול כמה חולצו.

זה מה שמאפשר לאבחן "למה מהדף הזה לא חולצו שלבים" בלי להביא אותו שוב — ובלי
לנחש. המפתח רואה אותו ב-☰ → יומן → יומן ייבוא, עם "העתק כטקסט" להדבקה בצ'אט;
ודרך טוקן הצפייה: `logs.php?token=…&view=import&format=text`. בניגוד ליומן
הכללי, כאן **נשמר** טקסט של מתכונים — זו המטרה. נמחק אחרי 60 יום / 3000 שורות,
ושורד מחיקת המתכון והמשתמש.

## היומן

כל בקשה ל-API, כל העלאה, אימות, איפוס, אירוע דוא"ל ושגיאת JavaScript מהדפדפן
נרשמים ב-`app_log` (`lib/log.php`): מי, מה, הצליח או נכשל, כמה זמן. כשל שהמשתמש
גרם לו (4xx) הוא `warn`, תקלה שלנו (5xx) היא `error`. סיסמאות, כתובות דוא"ל
וטקסט של מתכונים ותגובות **אינם** נרשמים — מהקלט נשמרים רק שדות מרשימה סגורה.
היומן נמחק אחרי 30 יום או 50 אלף שורות.

המפתח רואה אותו ב-☰ → יומן, ויכול ליצור **טוקן צפייה** עם תוקף (חצי שעה, שעה,
יום, שבוע או מותאם) ולהעביר קישור: `logs.php?token=…` — קריאה בלבד, בלי כניסה,
עד שהתוקף פג או שהטוקן בוטל. `&format=text` נותן טקסט להדבקה בצ'אט, `&format=json`
נותן JSON. במסד נשמר רק ה-hash של הטוקן.

עדיין לא: תמונה בתגובה (סעיף 7 באפיון אומר "כן, אחת" — נדחה עד שיהיה ביקוש).

## רשימת קניות, מצב בישול, הדפסה

**רשימת קניות** (`lib/shopping.php`): בכל מתכון "🛒 לרשימת קניות" — לרשימה קיימת או
חדשה, עם המרת המנות שמוצגת כרגע. האיחוד על השכבה המחושבת: אותו מוצר + אותה יחידה
מתחברים (300 + 200 גרם קמח = 500, "מ-2 מתכונים"); יחידות שונות של אותו מוצר נשארות
שורות נפרדות; רכיב בלי שכבה מחושבת נשאר כטקסט. השורות נשמרות — סימון "נקנה" שורד
הוספת מתכון (בנייה מחדש לפי שם+יחידה). שורות ידניות, שיתוף (Web Share או העתקה),
"נקה מסומנים" (ידני מסומן נמחק, מחושב רק מתבטל).

**מצב בישול** (`#/cook/:id`): שלב אחד גדול, כפתורי אצבע, רכיבי החלק מקופלים, שורת
חלקים לקפיצה, "בוצע" נשמר לכל משתמש (`cooking_progress`), Wake Lock שהמסך לא
יכבה, וטיימרים מזמנים שמופיעים בטקסט השלב ("10 דקות", "שעה") עם רטט וצפצוף בסיום.

**הדפסה**: "🖨 הדפסה" במתכון; `@media print` מסתיר ניווט, תגובות, פתק ותיעוד.
עדיין לא: מדיה, תגובות, מועדפים, רשימת קניות, מצב בישול.

| מה | איפה |

| דף הכלי | `index.html` |
| עיצוב | `assets/css/app.css` |

הסיר המתבשל שבדף הוא **מציין מקום**: ציור קווים על `<canvas>` בלי שום ספרייה,

`assets/css/app.css` ו-`assets/js/app.js` מיועדים להיות מוחלפים באפליקציה
עצמה.

## מה טרם הוכרע

האפיון כולו. אלה ההכרעות שקודמות לקוד, מפני שכל אחת מהן מזיזה את המבנה:

- **מה נשמר ואיפה** — רק בדפדפן (`localStorage`/IndexedDB), או גם בשרת
  ב-PHP + קובץ/מסד נתונים כמו ב-`claude-tasks` ו-`renovation-punchlist`.
- **מי כותב ומי קורא** — משתמש אחד, או כמה אנשים שחולקים אותו אוסף.
- **מה יש במתכון** — מצרכים עם כמויות ויחידות, שלבי הכנה, זמנים, תמונות,
  קטגוריות, מקור.
- **מה עושים איתו** — חיפוש וסינון, מצב בישול שלב-אחר-שלב, שינוי כמויות לפי
  מספר מנות, רשימת קניות, הדפסה או ייצוא.
- **עבודה בלי אינטרנט** — אם נדרשת, היא משפיעה על בחירת האחסון מלמטה ולא
  מתווספת אחר כך.

## כשהאפליקציה תיכנס לכאן

- **נקודת הכניסה** — חייבת להישאר `recipes-app/index.html`, כי לשם מצביע
  הכרטיס בדף הכלים.
- **נתיבים יחסיים** — נכסים נטענים ב-`./assets/...`. נתיב שמתחיל ב-`/` נשבר
  בשרת, מפני שהאתר יושב תחת `/mini_projects/` ולא בשורש הדומיין.
- **תיקיית נתונים** — אם האפליקציה תשמור נתונים בצד שרת, התיקייה שנכתבת חייבת
  `--exclude` משלה ב-`.github/workflows/deploy.yml`. בלעדיו כל פריסה תדרוס את
  המתכונים שנשמרו, כמו שכבר מוגדר ל-`renovation-punchlist` ול-`claude-tasks`.
  זו הנקודה שצריך להכריע **לפני** שנכתב קוד שמירה, לא אחריו.

## שערי בדיקה בפריסה

`deploy.yml` בודק תחביר של כל קובץ `.php` ושל כל קובץ `.js` לפני שהוא מעלה
משהו, ונעצר בשגיאה. קוד צד־שלישי מוקטן פטור מהבדיקה רק אם הוא יושב תחת
`vendor/`; ספרייה חיצונית שתיכנס לכאן בשם אחר — תיבדק, ועלולה להפיל פריסה.

## פריסה

התיקייה נפרסת אוטומטית עם שאר הריפו דרך `.github/workflows/deploy.yml`, ללא
הגדרה ייעודית. אין כאן כרגע קוד PHP ואין תיקיית נתונים.

## ממצאים

### 🔴/🟡-גבוה — נקודה בסוף שם המארח עוקפת את הצמדת ה-IP ומחזירה DNS rebinding ל-webhook
`kol-maroko/lib/forms.php:162-189` (`forms_hook_post`), בצירוף `forms_hook_url_check:95` ו-`forms_hook_set:120`.

**המנגנון שאמור להגן** (ספק §2.3, וההערה בקוד שורה 73): הכתובת נבדקת, ה-DNS נפתר, כל ה-IP נבדקים
מול טווחים פנימיים, ו**החיבור מוצמד ל-IP שנבדק** עם `CURLOPT_RESOLVE` — "אין DNS rebinding".

**הכשל:** `forms_hook_post` מחשב את `$host` עם `rtrim(..., '.')` (מסיר נקודה סופית), מצמיד
`"$host:443:$ip"` ב-CURLOPT_RESOLVE — אבל מעביר ל-`curl_init($url)` את ה-URL **הגולמי, עם הנקודה**.
curl מתייחס ל-`host.` ול-`host` כמפתחות מטמון שונים, ולכן **מתעלם מההצמדה ופותר את `host.` מחדש ב-DNS**.
אימות חי (בלי פרוקסי):

```
host שמוצמד ל-RESOLVE: 'attacker.example.com'
URL ל-curl: 'https://attacker.example.com./x'  (עם נקודה)
* Could not resolve host: attacker.example.com.   ← curl פתר מחדש, ההצמדה ל-192.0.2.9 לא חלה
```

`forms_hook_url_check('https://attacker.example.com./x')` → **עבר** (גם הוא מסיר את הנקודה),
וה-URL נשמר כפי שהוא (`forms_hook_set` שומר את `$url` הגולמי).

**תרחיש כשל קונקרטי:** מפרסם מגדיר webhook ל-`https://evil.example.com./in` (שליטה ב-DNS של הדומיין).
בעת `gethostbynamel('evil.example.com')` ה-DNS מחזיר IP ציבורי (TTL 0) → עובר את `forms_hook_ip_ok`.
רגע אחרי, curl פותר את `evil.example.com.` בעצמו → ה-DNS מחזיר `127.0.0.1` / `169.254.169.254` →
השרת (המשותף, cPanel) ניגש ל-loopback / למטא-דאטה של הענן / לשירות פנימי של הפלטפורמה. זו בדיוק
ההתקפה שההצמדה אמורה לחסום. ללא הנקודה — curl משתמש בהצמדה והרביינד נחסם; הנקודה פותחת מחדש את החלון.

**תיקון:** להצמיד את ה-RESOLVE לשם שבאמת נשלח, או לדחות/לנרמל נקודה סופית ב-`forms_hook_url_check`
(למשל להחזיר שגיאה כש-`rtrim($host,'.') !== $host`, או לבנות את ה-URL מחדש עם ה-host המנורמל).
הערה: אותו דפוס קיים גם ב-`rec_url_check` / `font_http` (A2/V9) — כדאי לתקן במקור המשותף.

### 🟡 — `forms_hook_ip_ok` חלש מ-`font_ip_ok` (V9): CGNAT ועוד טווחים שמורים עוברים
`kol-maroko/lib/forms.php:102-105`.

`forms_hook_ip_ok` משתמש רק ב-`FILTER_FLAG_NO_PRIV_RANGE | NO_RES_RANGE` (זהה ל-`rec_ip_public`,
כפי שהספק דורש "אותה בדיקה של A2"). אבל זו בקשה יוצאת מהשרת, בדיוק כמו הגופנים, ו-`font_ip_ok` (V9)
חוסם יותר. השוואה חיה:

| IP (תשובת DNS אפשרית) | forms_hook_ip_ok | font_ip_ok (V9) |
| --- | --- | --- |
| `100.64.0.1`, `100.127.255.254` (CGNAT 100.64/10) | **מותר** | נחסם |
| `198.18.0.1` (benchmark 198.18/15) | **מותר** | נחסם |
| `192.0.0.170` | **מותר** | נחסם |
| `224.0.0.1` (multicast) | **מותר** | נחסם |
| `169.254.169.254` (מטא-דאטה) | נחסם | נחסם |
| `::1`, `fc00::/7`, `fe80::`, `::ffff:127.0.0.1` | — ראו למטה — | — |

הכי מהותי לרשימת ההתקפות במשימה: **`100.64/10` (CGNAT) עובר** — טווח שנפוץ ברשתות פנים של ספקי
ענן/אירוח. `169.254.169.254` עצמו **כן** נחסם (NO_RES_RANGE). המלצה: לאמץ את `font_ip_ok` גם כאן.

*הערה (⚪):* `::ffff:127.0.0.1`, `::ffff:10.0.0.1` ו-`fc00::/7` — `forms_hook_ip_ok` מתיר את
ה-`::ffff:` (בניגוד ל-font), אך בפועל `gethostbynamel` מחזיר IPv4 בלבד ו-RESOLVE מצמיד IPv4, ולכן
הנתיב הזה אינו נגיש דרך ה-webhook. `fc00::/7` ו-`::1` — נחסמים. פער תיאורטי בלבד, להקשחה.

### שאר וקטורי ה-SSRF — נבדקו, תקינים
טבלת `forms_hook_url_check` המלאה: `scratchpad/ssrf-v16c.out`. נחסמים כנדרש:
loopback/פרטי/link-local ב-IPv4 ו-IPv6 (`127.0.0.1`, `[::1]`, `0.0.0.0`, `169.254.169.254`,
`[fc00::1]`), עשרוני/אוקטלי/hex (`2130706433`, `0x7f000001`, `017700000001`, `127.1`),
`localhost`/`*.local`/`*.internal`/`intranet`, userinfo (`a@127.0.0.1` — גם עם `#@`/`?@` ה-host
הנכון נלקח), http/ftp/javascript/file/gopher, רווח/`\n`/`\`, IDN לא-ASCII (`מפה.co.il`, `①②⑦`),
פורט ≠443 (`:8443`). DNS rebinding (תשובה פנימית, ותשובה מעורבת ציבורי+פרטי) נחסם ב-`forms_hook_post`
(כל ה-IP נבדקים). הפרוטוקולים מוגבלים (`CURLOPT_PROTOCOLS`/`REDIR_PROTOCOLS`=HTTPS), בלי הפניות
(`FOLLOWLOCATION=false`, `MAXREDIRS=0`), timeout 5s/connect 4s, תגובה חסומה ל-64KB. `xn--`
(punycode) עובר כצפוי (ASCII חוקי), ו-`host.` — הממצא למעלה.

  (auth.php:31). `forms_hook_state` = editor (קריאה). נבדק בטסטים (עורך → 403).

  ניסיונות חוזרים מתוזמנים. פנייה מהתצוגה-החיה (`test`) **אינה** נשלחת החוצה (נבדק).

### טפסים — תקין
אימות קלט/גודל/קצב/ספאם (מלכודת + `_t`) — כולם ב-M5 הקיים, לא נגעו. V16c רק הוסיף את קריאות ה-hook
אחרי השמירה. הרישום נגזר מה-HTML (`forms_scan`) — שדה שנוסף בבונה נשלח מיד (נבדק). קבצים — נדחים
("קובץ מצורף"). הבונה (`kit-form.js`) רץ בעורך בלבד, כל פלט ה-HTML מקודד (`escT`/`escA`),
`checkRedirect` חוסם `javascript:`/`data:`/סכמות לא-https, `checkPattern` מאמת regex. אין תיקיית
נתונים חדשה — הכול ב-`settings`/`form_entries` שבתוך `data/kol.sqlite` (כבר מוחרג בפריסה). אין צורך
ב-`--exclude` נוסף. הזרקת CSV/HTML בתצוגה — `inbox_csv` לא שונה ב-V16c (M5).

### מפה / רשתות / lottie — תקין
- **מפה** ו-**הטמעת פוסט**: `iframe` נטען רק אחרי לחיצה, מקורות חיצוניים מוצהרים ב-`kit.json`
  (`external`/`links`) כדי להיכנס לרשימה הגלויה של C1. ה-sandbox כולל `allow-scripts allow-same-origin`
  יחד (ידוע שמאפשר לתוכן להסיר סנדבוקס משלו) — מקובל כאן כי זה תוכן צד-שלישי בהסכמה (Google/רשתות)
  שנטען רק בלחיצה מפורשת; תואם את הדרישה. social-embed מגביל ל-`https:` בלבד ב-JS.
- **כפתורי שיתוף / אייקוני רשתות**: קישורי `share` רגילים ו-SVG מוטמע (Simple Icons CC0) — בלי סקריפט
  של רשת, בלי טעינה חיצונית. תקין.
- **lottie 1.0.1**: `data-kol-src` נטען רק מאותו origin (`u.origin !== new URL(base).origin` → לא נטען).
  נתיב יחסי = אותו origin. תואם "lottie רק מאותו origin".

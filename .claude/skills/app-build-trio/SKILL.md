# שלושה צ'אטים לאפליקציה חדשה

הדפוס: אדם פותח לאפליקציה חדשה שלושה צ'אטים במקביל, לכל אחד תפקיד אחד.
הסקיל הזה מקים את ה-**תיאום** ביניהם: תיקיית מצב בריפו, כללי כתיבה, ופרומפטים פתיחה מוכנים להעתקה.

> אין ערוץ הודעות חי בין סשנים (`CLAUDE.md`). כל מה שעובר בין הצ'אטים עובר בקבצים בגיט, או דרך האדם שמעתיק הודעה.

## התפקידים

| צ'אט | מה הוא עושה | מה הוא **לא** עושה |
| --- | --- | --- |
| **בקרה** | מחזיקה את התוכנית, מחלקת את העבודה לשלבים, מאשרת כל שלב לפני שהוא נסגר, מחליטה מה הבא | לא כותבת spec ולא כותבת קוד |
| **אפיון** | כותב `spec.md` (מה האפליקציה עושה, למי, מסכים, כללים), מענה לשאלות הבקרה | לא מממש |
| **קוד** | ממממש לפי ה-spec המאושר, בענף משנה, פותח PR | לא משנה את ה-spec. שאלה עליו — ל-`handoffs/` |

## תיקיית המצב

כל אפליקציה בתיקייה משלה בריפו: `builds/<app-id>/`. `<app-id>` = שם באנגלית, kebab-case.

```
builds/<app-id>/
  STATUS.md        ← הבקרה בלבד. המצב הנוכחי, השלב הבא, מי עושה מה
  spec.md          ← האפיון בלבד (צ'אט אפיון). נעול אחרי אישור הבקרה
  build-log.md     ← הקוד בלבד. מה נבנה, מה נבדק, מה פתוח, קישורי PR
  handoffs/        ← הודעות בין הצ'אטים, קובץ לכל הודעה
    NNN-<from>-to-<to>.md
```

**כלל הכותב היחיד:** כל קובץ נכתב רק על ידי בעליו. צ'אט אחר רק קורא. כך אין עריכות מתנגשות, גם כששניים עובדים במקביל.

## פורמט הודעה (`handoffs/`)

```markdown
---
from: spec | control | code
to: spec | control | code
kind: question | decision | ready-for-review | done | blocked
date: YYYY-MM-DD
---

מה קרה / מה נדרש — במשפט או שניים.
מה מצופה מהצד השני.
```

מספור `NNN` רץ בסדר עולה. הצד המקבל קורא את כל ההודעות ב-`to:` שלו שטרם טופלו, ומסמן טיפול בשורה ב-`STATUS.md`.

## זרימה

1. **בקרה** פותחת `STATUS.md` עם שם האפליקציה, המטרה, והשלב `spec`.
2. **אפיון** כותב `spec.md` ואז `handoffs/NNN-spec-to-control.md` מסוג `ready-for-review`.
3. **בקרה** קוראת, ומחליטה: `decision` חוזר לאפיון לתיקון, או אישור. באישור היא מעדכנת `STATUS.md` לשלב `build` ומשאירה `spec.md` נעול.
4. **קוד** קורא את `spec.md` המאושר, פותח ענף משנה מ-`main`, ממממש, ורושם ב-`build-log.md`. שאלה על ה-spec → `handoffs/…-code-to-spec.md` ו**ממשיך בדברים שלא תלויים בה**.
5. **קוד** פותח PR טיוטה ל-`main` ומשאיר handoff `done` לבקרה עם הקישור.
6. **בקרה** בודקת מול ה-spec ומעדכנת `STATUS.md`. היא לא מוזגת; מיזוג נשאר לאדם.

## פרומפטים לפתיחה

אלה הטקסטים שהאדם מעתיק לכל צ'אט. הם בכוונה קצרים, כי הכללים כבר בקבצים.

**בקרה:**
```
אנחנו בונים אפליקציה חדשה בשם <app-id>: <מטרה במשפט>.
אתה צ'אט הבקרה. קרא את builds/<app-id>/STATUS.md ואת handoffs/ לפני כל דבר.
אתה לא כותב spec ולא קוד. אתה מחליט, מאשר שלבים, ומעדכן STATUS.md בלבד.
```

**אפיון:**
```
אתה צ'אט האפיון של <app-id>. קרא builds/<app-id>/STATUS.md.
כתוב את builds/<app-id>/spec.md, ואז handoff מסוג ready-for-review לבקרה.
אתה כותב רק ב-spec.md ובתיקיית handoffs/ (רק הודעות from: spec).
```

**קוד:**
```
אתה צ'אט הקוד של <app-id>. קרא builds/<app-id>/spec.md (רק אחרי שה-STATUS מסמן build).
ממש בענף משנה מ-main, רשום ב-builds/<app-id>/build-log.md, ופתח PR טיוטה.
שאלות על ה-spec — handoff ל-spec, לא שינוי של ה-spec בעצמך.
```

## כללים

- **ענף אחד לכל אפליקציה**, מ-`main` המעודכן. לא עובדים ישירות על `main`.
- **PR ל-`main` בלבד.** האתר פורס רק מ-`main` (ראה `.github/workflows/deploy.yml`). לא מוסיפים ענף עם טריגר פריסה משלו.
- **כלי חדש = `app.json` בתוך התיקייה שלו.** לא נוגעים ב-`index.html` הראשי.
- **קוד של האפליקציה נכנס לתיקייה משלה בריפו** (`<app-id>/`), לא לתיקיית `builds/`. `builds/` הוא רק מצב תיאום.
- **אסור לשנות `spec.md` אחרי אישור הבקרה.** שינוי דורש handoff `decision` חדש מהבקרה.
- **לא לכתוב סודות או אסימונים לאף קובץ בתיקיית `builds/`.**
- **הודעות ותיעוד בעברית, שמות קבצים בקוד באנגלית.**

## מה הסקיל לא עושה

- לא פותח צ'אטים בעצמו. הוא נותן את הפרומפטים, והאדם פותח את שלושת הצ'אטים.
- לא מאמת שהאפליקציה עובדת. זה בתחום של הקוד ושל הבדיקה.
- לא מחליף את `chat-dev-team` כשצריך מבקר, QA וכמה מתכננים במקביל.

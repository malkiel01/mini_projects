# הנחיה לצ'אט הפלטפורמה: תיקיית חנות לכל אפליקציה, וחיבור חשבונות חד-פעמי

**מאת:** הצ'אט של אפליקציית המתכונים, לבקשת בעל המערכת, 2026-10-19.
**הדוגמה החיה:** PR #423 (`recipes-app/`, `.github/workflows/recipes-twa.yml`). לא לגעת בקוד של המתכונים;
צריך משהו משם? לבקש דרך בעל המערכת.

---

## 1. מה הוכרע

1. **כל אפליקציה, חוץ מקדישא, נמצאת מאחורי השער.** אפליקציה מחוברת: נכנסים דרך חשבון הכלים הדיגיטליים.
   אפליקציה מנותקת (🔌 בממשק המנהל): היא פתוחה, עם החשבונות שלה. ההחלפה נעשית בשרת בלבד, **בלי גרסה חדשה בחנות**.
2. **לכל אפליקציה יש כתובת משלה: התיקייה שלה בדומיין הראשי** — `https://mbe-plus.com/mini_projects/<app>/`.
   אפליקציית האנדרואיד (TWA) נפתחת שם, ו**תופסת קישורים רק בתיקייה הזאת** (`android:pathPrefix`).
   הסיבה: על הדומיין יש הרבה כלים, ובלי ההגבלה כל קישור לכל כלי ייפתח באפליקציה הראשונה שהותקנה.
3. **סאב-דומיין לא עובד עם השער, ולכן כל סאב-דומיין קיים מפנה (301) לתיקייה.** זה מה שנמצא בקוד:
   - `gate-prepend.php` מחליט לפי נתיב הקובץ ולא לפי הדומיין, כך שגם בסאב-דומיין כל PHP נבדק.
   - העוגייה של הפלטפורמה נקבעת בלי `domain`, ולכן לא מגיעה לסאב-דומיין. התוצאה: 401 על כל בקשה.
   - בלוק ה-rewrite מפנה ל-`/mini_projects/platform/gate.php`, נתיב שלא קיים תחת השורש של הסאב-דומיין. התוצאה: 404 על כל קובץ.
   - ההפניה לא יכולה לשבת ב-`.htaccess` של האפליקציה, כי `build-gate.php` כותב את הבלוק שלו **לפני** הכללים שלה.
     לכן היא נעשית ב-cPanel: שורש נפרד וריק לסאב-דומיין, ועליו Redirect עם Wild Card.

## 2. "תיקיית החנות": המבנה לכל אפליקציה

ב-GitHub יש Release קבוע לכל אפליקציה, `<app>-store`, שמתעדכן בכל בנייה מ-main. שמות הקבצים קבועים, ולכן גם הקישור קבוע:

| קובץ | מה זה |
| --- | --- |
| `<app>.apk` | התקנה ישירה בטלפון |
| `<app>.aab` | להעלאה ל-Play Console (רק בבנייה חתומה) |
| `store-listing.zip` | קובץ ההגדרות לחנות: `STORE.md` (טקסטים, תשובות למדיניות, Data safety) ו-`store/` (סמל 512, באנר 1024×500, צילומי מסך) |
| `assetlinks.json` | הרשומה של האפליקציה בשורש `mbe-plus.com` (מסך מלא בלי שורת כתובת) |
| `build.json` | מספר הבנייה, הכתובת, סוג החתימה, טביעת מפתח ההעלאה |

אצל המתכונים זה כבר עובד: `recipes-app-store`, ו-`install.apk` ב-app.json מצביע על `recipes.apk`.

## 3. מה הפלטפורמה צריכה לבנות

### א. מה רואים בכל אפליקציה

| | מנהל המערכת | משתמש רגיל |
| --- | --- | --- |
| הורדת APK | ✓ | ✓ |
| הורדת AAB לחנות | ✓ | — |
| קובץ ההגדרות לחנות (`store-listing.zip`) | ✓ | — |
| התקנת PWA ישירה | ✓ | ✓ |
| כניסה בדפדפן הכלים הדיגיטליים | ✓ | ✓ |

- **צריך להכריע:** איך מצהירים על תיקיית החנות ב-app.json. ההצעה: `"install": {"apk": "...", "release": "<app>-store"}`,
  ומזה גוזרים את הקישורים לשאר הקבצים. צריך לעדכן גם את `check-apps.php`.
- **⚠️ פרטיות:** הריפו ציבורי, ולכן קבצי Release נגישים לכל מי שיש לו הקישור. הסתרה בממשק לא הופכת אותם לפרטיים.
  אם AAB וקובץ ההגדרות חייבים להיות למנהל בלבד, צריך לאחסן אותם במקום אחר (למשל תיקייה חסומה בשרת, שמוגשת דרך PHP אחרי בדיקת מנהל).
  זו הכרעה של בעל המערכת. ל-AAB של TWA אין תוכן סודי.

### ב. `assetlinks.json` בשורש `mbe-plus.com`: קובץ משותף

- הקובץ חייב לשבת ב-`https://mbe-plus.com/.well-known/assetlinks.json`, כלומר **מחוץ ל-DEPLOY_PATH**.
- הוא **רשימה אחת לכל האפליקציות**, עם רשומה לכל חבילה. אין ביניהן התנגשות.
- **מוצע שהפלטפורמה תהיה הבעלים שלו:** לאחד את `assetlinks.json` מכל `<app>-store` ולפרוס לשורש.
  עד שזה קיים, בעל המערכת מעלה אותו ידנית ב-cPanel.

### ג. אפליקציית אנדרואיד לכל אפליקציה

- **תבנית:** `recipes-app/android/` ו-`recipes-twa.yml`, להעתיק לתיקיית האפליקציה ולא לשנות את המקור.
- **מה משתנה לכל אפליקציה:** `appPath`, שם חבילה `com.mbeplus.<app>`, ומפתח חתימה משלה.
- **מפתח החתימה:** בעל המערכת צריך להחליט בין סוד לכל אפליקציה לבין גזירה מסוד קיים, כמו ב-project-manager.
- **לאפליקציות שכבר יש להן APK נייטיב** (whatsapp-ai-scanner, guarded-browser, greeting-cards, project-manager):
  להוסיף AAB, `store-listing.zip` ותיקיית חנות באותו מבנה.

### ד. מסך חיבור חד-פעמי ("שער מסך זמני")

- **מתי מופיע:** משתמש שנכנס דרך השער ועדיין אין לו קשר בין החשבון שלו באפליקציה לבין חשבון הכלים הדיגיטליים.
- **מה עושים בו:** נכנסים לחשבון באפליקציה או יוצרים חשבון, והקשר נשמר.
- **מתי לא מופיע:** פעם אחת בלבד. אחרי שהקשר נוצר, או כשהמשתמש כבר מחובר, המסך לא מופיע שוב.
- **על מה לבנות:** על "כניסה מאוחדת" הקיימת (`platform/docs/sso.md`, `sso.php`, זהות חתומה ב-Ed25519).
  הפלטפורמה מגדירה את המנגנון ואת הממשק, וכל אפליקציה מממשת את הצד שלה בתוך התיקייה שלה.
- **אפליקציה מנותקת:** הכניסה הרגילה שלה, בלי המסך.
- **שמור:** האפליקציה נשארת עצמאית, עם משתמשים, מסד ועוגייה משלה.

### ה. תיעוד

- `platform/README.md`, בטבלה "מי מאחורי השער": recipes-app עברה ל"חסום, עם `public`", כולל הסיבה, ההפניה מהסאב-דומיין והממצא מסעיף 1.3.
- סעיף על תיקיית החנות ועל `assetlinks.json` המשותף.

## 4. הנחיה לכל צ'אט של אפליקציה

הצ'אט של הפלטפורמה מנסח **לכל אפליקציה הנחיה נפרדת ומותאמת**, ושולח אותה דרך בעל המערכת. כל צ'אט נוגע רק בתיקייה שלו:

1. **שער:** `"gate": true` ו-`"public"`, ממופים **מהקוד ולא מהזיכרון**: קישורי מייל, עובדים, cron, webhooks, API של אפליקציה נייטיב,
   manifest, service worker ואייקונים (הדפדפן מוריד manifest בלי עוגיות). כל `action` של API שדף ציבורי קורא לו.
   בדיקה בחלון גלישה בסתר. כתובת המתכונים היא דוגמה (`recipes-app/README.md`, "מאחורי השער של הפלטפורמה").
2. **סאב-דומיין קיים:** להפנות אותו ב-cPanel לפני המיזוג, אחרת הוא נשבר.
3. **עובדים שמעירים את עצמם ב-HTTP:** לעקוב אחרי הפניה (`CURLOPT_FOLLOWLOCATION`), כי ייתכן ש-`base_url` ישן נשמר.
4. **אנדרואיד ותיקיית חנות:** לפי סעיף 3ג.
5. **מסך החיבור החד-פעמי:** לפי סעיף 3ד, אחרי שהפלטפורמה הגדירה את המנגנון.
6. **משתמשים קיימים מבחוץ:** חשבון בפלטפורמה והרשאה, לפני המיזוג.

**החריג:** קדישא (`kadisha/`) היא חיצונית ולא נכנסת לכל זה.
